FitCachePP

Transparent local-storage caching for memory-mapped data loading on Frontier

Training jobs that read data with mmap (LLM token shards, GNN feature tables, vision tar shards) get the data served transparently from a fast node-local cache instead of the parallel filesystem — with no change to the application. Below: what the system does (shown as diagrams), then how much it helps (measured, checksum-verified).

The problem

The old cache hooked read()/pread(). But modern loaders read by memory-mapping a file and page-faulting — they never call read(), so they slipped straight past the cache to Lustre.

On the workloads we target, the cache measured 0 cache hits — every byte came from Lustre. (Lustre streams at ~2 GB/s sequentially, but sparse-random 4 KB page-faults crawl at ~3–4 MB/s — which is why the access pattern decides the win.)

What we do — 1 / 3

Transparent mmap cache path

We intercept mmap. On a warm hit, the client itself computes where the cached copy lives (the same deterministic hash the server uses), checks it's complete, and hands back a direct mmap of that local file — the kernel then page-faults from local storage (the DRAM/tmpfs or NVMe tier — whichever holds the file), with no network round-trip.

The warm-hit path has no RPC: the client finds the cached file by computing its path, then maps it directly.

Why map a local file instead of fetching the bytes over the network? Our first design fetched the data over Mercury RPC at mmap time. It was the slowest option — so the read path now touches no network at all.

Single-stream bandwidth. The RPC fetch (≈0.9) and Lustre (≈2.0 GB/s) are from our design notes; the local-tier bar (*) is an estimate showing it is faster than Lustre. The point is the ordering — the old RPC fetch was slower than Lustre itself, so we dropped it.

What we do — 2 / 3

Access-aware placement

A warm hit needs the file on the same node as the rank reading it. Default hashing scatters a node's files across the cluster, so it misses about half of its own data. We route each file's cached copy to its own node.

Same data, two placements. Node-local routing turns 22 cross-node misses into 0 (measured: Megatron, N=2).

For workloads where each node reads a disjoint slice, the same routing stores the corpus once instead of replicating it on every node:

What we do — 3 / 3

Sidecar recovery

Each cached file gets a tiny .meta sidecar. When the cache service restarts, it rebuilds its state from those sidecars in seconds — the cache survives the restart instead of re-fetching everything from the filesystem.

Metadata-restore-only sweep: restore time is independent of how many objects are cached (~1 KB each). (A full DINOv2 recovery, which also re-checks the data files, takes ~8 s — a different, heavier path.)

The warm epoch is flat at 175–178 s across 32/64/128 nodes (the client-local resolver adds no coordination cost at scale). The speedup (14.7× / 5.3× / 6.0×) varies only because the native baseline swings with Lustre's time-of-day contention — warm is the stable quantity. (256-node native hit 5890 s ≈ 98 min; warm pending.)
The warm path is multi-tier, not NVMe-only. A controlled run served 48 warm hits from the DRAM (/tmp tmpfs) tier, bit-identical and at parity with NVMe — the resolver maps whichever local tier holds the file (DRAM → NVMe).

Honest framing

  • This accelerates data loading, not GPU compute — we speed up the I/O the loader does.
  • Warm-hit runs use a pre-staged cache; we also report the amortized view including that staging cost (break-even 1–4 epochs).
  • Magnitude is reported per regime — the GNN win is ~6× vs the most favorable Lustre native and 22–30× vs cold Lustre; dense-sequential wins are a modest ~1.2–1.95×. The big wins come from access patterns Lustre handles poorly (sparse random).
  • Tier-general, served from NVMe here — the path also warm-hits the DRAM/tmpfs tier (48 hits, bit-identical); on Frontier the working sets (640 GiB–902 GB/node) exceed node RAM, so they land on the NVMe burst buffer, which also keeps the baseline from cheating via the page cache.
