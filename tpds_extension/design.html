FitCachePP TPDS Extension — Final Design

System view of the mechanisms that back the paper claims. Companion pages: EXPERIMENTS_STATUS.html · experiments.html · paper.html.

Pipeline overview

FitCachePP is an LD_PRELOAD client paired with Mercury-RPC metadata/data servers (default 4 servers/node). An application's file access is intercepted transparently; on a warm hit the data is served from a node-local cached copy held in a local cache tier (DRAM/tmpfs → PMem → NVMe), on a cold miss from the parallel filesystem (PFS) while the file is promoted to local cache for next time.

app open()/mmap()  ──►  LD_PRELOAD client
                          │
                ┌─────────┴──────────┐
            warm hit               cold miss
                │                     │
   resolve cached path          native PFS read/mmap
   (deterministic, no RPC)            │
                │              enqueue promotion (open-time)
   __real_mmap of cached file   ──►  data mover copies to a local
   (page-fault from local tier)      tier (DRAM-first → PMem → NVMe)
                                     + writes .meta sidecar

The cache is tier-general: the data mover places a promoted file DRAM (tmpfs) first, then PMem, then NVMe by remaining capacity, and the resolver probes the tiers in the same order and maps whichever holds the file. On Frontier the warm-hit experiments were served from the NVMe tier (per-node burst buffer /mnt/bb). What matters is the per-node working set, not the total dataset: these sweeps keep it > the 512 GiB node RAM on purpose by replicating the set on every node (Megatron stages all 40 shards = 640 GiB/node; GNN stages the whole feature files ~902 GB/node; DINOv2 full-corpus is shared, 541 GB/node), so aggregate DRAM across nodes does not shrink it and a per-node tmpfs cannot hold it. PMem is unset (Frontier has no PMem). A partitioned access pattern (DINOv2 disjoint = the Mechanism-2 placement) is the exception — at 16 nodes each holds ~34 GB, which fits tmpfs — but then the Native_mmap_PFS baseline page-caches it too, washing out the sustained warm-hit gap. So NVMe is the correct tier for the sustained claim; a DRAM datapoint would be a different (cold-start) experiment.

Mechanism 1 — Transparent mmap cache path DONE

The warm-hit path resolves the cached copy with fitcache_resolve_cached_path(): client-side, deterministic hash-bin, with a size-match completeness gate, and no RPC. On match it calls __real_mmap on the cached file in whichever local tier holds it (DRAM/PMem/NVMe), so the kernel page-faults directly from that local tier. On a cold miss it uses the native PFS mmap and enqueues promotion at open time (the mmap/fd-reuse pattern made a close-time RPC skip leave the cache empty). The populate path copies in ≤1 GiB chunks and the server loops on short reads, so files larger than ~2 GiB are no longer truncated. Eviction safety relies on Linux unlink-while-mapped semantics protecting active mappings.

Mechanism 2 — Access-aware mmap cache placement DONE

A warm hit requires the cached file on the requester's own node. Placement is decided in select_server_for_path() (src/cross_job/fitcache_cross_job.cpp):

  • Default hash — modulo_select() = fnv1a64(path) % total_servers. Saves space but scatters a node's mmap set across the cluster, producing remote/fallback misses at N≥2.
  • node_local branch — gated by FITCACHE_MMAP_PLACEMENT=node_local. Routes promotion to the node's own slots [nodeid·spn, (nodeid+1)·spn), where spn = total_servers / SLURM_NNODES and nodeid = SLURM_NODEID. Logs placement_policy=node_local and a per-node local/remote summary. Default hash path is unchanged.

Two access patterns ride on top of node_local: shared (all nodes read the same set, each replicates locally) and partitioned (nodes read disjoint sets via the cc12m bench's disjoint mode, so each node caches only its own shards at ~1× global copies).

Mechanism 3 — Sidecar cache-state recovery Supporting

The data mover writes a .meta sidecar per cached file on organic promotion. After a metadata-service restart, restore_from_sidecars rebuilds the server-side cache-state map (eviction/promotion accounting). The client warm-hit resolver is independent of the server map: it recomputes the deterministic cached path and stats the local cache tier, so as long as the cached files persist on local storage (the burst buffer in the Frontier runs) the client warm-hits in both the with- and without-sidecar arms. The sidecar therefore restores reusable cache state and reduces cold metadata recovery; it is not the bandwidth source.

Future work — cross-job cache sharing Future work

Cross-job sharing (FitCache_CROSS_JOB=1, HRW/peer-read path) remains future work only; no new compute is spent on it and it is not a claim in this paper. The single-job placement path (CROSS_JOB=0) is the one exercised by all reported experiments.

Invalid / rejected designs Rejected

  • Eager-populate via server + Mercury anon-mmap — rejected. It added a PFS→server→client hop and could not beat Native_mmap_PFS in any single-pass regime. Replaced by the client-side warm-hit direct local-tier path.
  • Single unbounded read()/bulk-RMA populate — invalid. The Linux kernel caps a single read near 0x7ffff000 (~2 GiB) and a single Mercury/libfabric bulk RMA caps near 2 GiB; neither was looped, truncating >2 GiB files. Fixed with the server short-read loop and ≤1 GiB chunked populate.
