FitCachePP TPDS Extension — Final Design

System view of the mechanisms that back the paper claims. Companion pages: EXPERIMENTS_STATUS.html · experiments.html · paper.html.

Pipeline overview

FitCachePP is an LD_PRELOAD client paired with Mercury-RPC metadata/data servers (default 4 servers/node). An application's file access is intercepted transparently; on a warm hit the data is served from a node-local cached copy held in a local cache tier (DRAM/tmpfs → PMem → NVMe), on a cold miss from the parallel filesystem (PFS) while the file is promoted to local cache for next time. The new piece is prefetch-informed migration: an application declares the files it is about to mmap() via fitcache_prefetch(path, replication_mode), and the owning server migrates the single cached copy to that node ahead of the read, overlapped with the current epoch's compute. The cluster therefore stores each file once (1×) instead of N×, while every read is still a warm local mmap.

app fitcache_prefetch(path)   ──►  LD_PRELOAD client ──► prefetch RPC (PREFETCH priority)
   (declared before mmap)                                    │
                                              owning server migrates the ONE copy
                                              peer ──► local tier (whole-file bulk xfer),
                                              overlapped with current-epoch compute

app open()/mmap()  ──►  LD_PRELOAD client
                          │
                ┌─────────┴──────────┐
            warm hit               cold miss
                │                     │
   resolve cached path          native PFS read/mmap
   (deterministic, no RPC)            │
                │              enqueue promotion (open-time)
   __real_mmap of cached file   ──►  data mover copies to a local
   (page-fault from local tier)      tier (DRAM-first → PMem → NVMe)
                                     + writes .meta file

The cache is tier-general: the data mover places a promoted file DRAM (tmpfs) first, then PMem, then NVMe by remaining capacity, and the resolver probes the tiers in the same order and maps whichever holds the file. On Frontier the warm-hit experiments were served from the NVMe tier (per-node burst buffer /mnt/bb); PMem is unset (Frontier has no PMem). Crucially, Frontier has no NVMe-oF / remote DAX, so a node cannot mmap a peer's NVMe directly. "Migration" is therefore a whole-file network transfer to the local tier — it only pays off when prefetched and overlapped with compute; performed lazily at mmap time it is no better than the existing per-read RPC fallback, which is exactly why the prefetch interface is load-bearing. With prefetch in place each node holds only its own 1/N partition, so the cluster keeps the dataset at 1× while reads stay warm local mmaps. For experiment numbers (cold→warm, warm→warm, 1× du) defer to experiments.html.

One system, three dependent mechanisms

FitCachePP is one system. The three mechanisms below are not independent features that happen to ship together — they are causally chained, and the headline warm-hit result only holds when all three are in place:

  1. Mechanism 1 (mmap cache path) delivers the speedup, but only if the cached copy is on the requester's own node — the win comes from page-faulting directly out of local storage with no network hop.
  2. Getting that single copy onto the requesting node ahead of the read is what Mechanism 2 (prefetch-informed migration + limited replication) provides. The application declares its files with fitcache_prefetch(); the owning server migrates the one cached copy peer→local, overlapped with compute, so the cluster stores the file 1× instead of replicating it N× — and Mechanism 1 then warm-hits it locally.
  3. The cache only stays useful across a job requeue or a service crash if the server can rebuild its state, which is what Mechanism 3 (.meta-file recovery) provides. Without it a restart makes the server-side map look empty and the promotion/eviction accounting is lost — so the migrated, locally-cached state survives a restart only because Mechanism 3 restores it.

The chain reads end to end: a warm mmap hit needs the file on the local node → prefetch migrates the single copy there (1×, not N× replication) → .meta recovery preserves that state across restarts. The per-mechanism sections below are the ablations that attribute the whole-system result to each mechanism; see experiments.html.

Mechanism 1 — Transparent mmap cache path DONE

The warm-hit path resolves the cached copy with fitcache_resolve_cached_path(): client-side, deterministic hash-bin, with a size-match completeness gate, and no RPC. On match it calls __real_mmap on the cached file in whichever local tier holds it (DRAM/PMem/NVMe), so the kernel page-faults directly from that local tier. On a cold miss it uses the native PFS mmap and enqueues promotion at open time (the mmap/fd-reuse pattern made a close-time RPC skip leave the cache empty). The populate path copies in ≤1 GiB chunks and the server loops on short reads, so files larger than ~2 GiB are no longer truncated. Eviction safety relies on Linux unlink-while-mapped semantics protecting active mappings.

Mechanism 2 — Prefetch-informed migration + limited replication DONE

A warm hit requires the cached file on the requester's own node, but on Frontier a node cannot mmap a peer's NVMe (no NVMe-oF / remote DAX). Rather than replicate the whole working set onto every node (N× storage), the application declares the files it is about to map and the owning server migrates the single cached copy there ahead of the read.

The prefetch interface

  • C API — extern "C" int fitcache_prefetch(const char *original_path, int replication_mode) in src/client/fitcache_multi_source_read.{h,cpp}, exposed as an LD_PRELOAD symbol via wrappers.c. Benchmarks drive it through benchmarks/fitcache_prefetch_shim.py (ctypes → fitcache_prefetch).
  • RPC + handler — fitcache_prefetch_in_t/out_t (carrying replication_mode and replication_cap) in src/comm/fitcache_comm.h; fitcache_prefetch_rpc_handler (src/comm/fitcache_comm_server.cpp:922) enqueues the request with PREFETCH priority. The mode/cap are forwarded through fitcache_comm_client.cpp:682.
  • The migration primitive — fitcache_server_migrate_file() (src/server/fitcache_data_mover.cpp:53) pulls the whole file peer→local in one bulk transfer (not the per-pread loop). It is invoked from the prefetch path (src/server/fitcache_server.cpp:237) and from open-time promote (fitcache_data_mover.cpp:584).

Replication modes

The declared replication_mode bounds how many copies the cluster keeps; it is recorded in the .meta file (src/cross_job/fitcache_persistent_meta.h) so it survives restarts:

ModeValueBehavior
SINGLE_COPY1One copy cluster-wide; migrate peer→local on demand. The 1× default for partitionable workloads.
BOUNDED_K2At most k copies (the replication_cap), for hot / concurrently-read files.
UNBOUNDED0The old replicate-all default (a copy on every reading node).

Lazy migration at mmap time is no better than the per-read RPC fallback; the benefit comes only when the declaration lets the server migrate ahead of the read and overlapped with the current epoch's compute. Each node then prefetches only its own 1/N partition, so partitionable workloads keep the dataset at 1× cluster storage (du-confirmed) while every read is a warm local mmap. Un-partitionable access (e.g. a sparse gather that can touch any row) cannot shrink to 1/N and falls back to a wider replication mode, but still wins the warm hit; see experiments.html for the per-workload breakdown.

Mechanism 3 — .meta file cache-state recovery Supporting

The data mover writes a .meta file per cached file on organic promotion. After a metadata-service restart, restore_from_sidecars rebuilds the server-side cache-state map (eviction/promotion accounting, including the recorded replication_mode). The client warm-hit resolver is independent of the server map: it recomputes the deterministic cached path and stats the local cache tier, so as long as the cached files persist on local storage (the burst buffer in the Frontier runs) the client warm-hits in both the with- and without-.meta file arms. The .meta file therefore restores reusable cache state and reduces cold metadata recovery; it is not the bandwidth source.

Future work — cross-job cache sharing Future work

Cross-job sharing (FitCache_CROSS_JOB=1, HRW/peer-read path) remains future work only; no new compute is spent on it and it is not a claim in this paper. The single-job placement path (CROSS_JOB=0) is the one exercised by all reported experiments.

Invalid / rejected designs Rejected

  • Whole-working-set replication (replicate-all) — superseded. Caching every node's entire working set gives N× the dataset (Megatron 640 GiB/node, GNN ~902 GB/node, DINOv2 541 GB/node). Replaced by prefetch-informed migration that keeps partitionable workloads at 1× while preserving the warm local mmap; the old behavior survives only as the explicit UNBOUNDED replication mode.
  • Lazy peer→local migration at mmap time — rejected as a standalone path. Without a prior declaration the whole-file transfer lands on the critical read path and is no better than the existing per-read RPC fallback; overlapping it with compute requires the fitcache_prefetch() interface.
  • Eager-populate via server + Mercury anon-mmap — rejected. It added a PFS→server→client hop and could not beat Native_mmap_PFS in any single-pass regime. Replaced by the client-side warm-hit direct local-tier path.
  • Single unbounded read()/bulk-RMA populate — invalid. The Linux kernel caps a single read near 0x7ffff000 (~2 GiB) and a single Mercury/libfabric bulk RMA caps near 2 GiB; neither was looped, truncating >2 GiB files. Fixed with the server short-read loop and ≤1 GiB chunked populate.
