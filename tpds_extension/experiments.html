Structure. Part 1 — Final results: three real workloads, 16→2048 GPUs FINAL

Measurement setup (identical across §1.1–1.2; §1.3 uses its own proven harness). Real data-loading code paths — Megatron's IndexedDataset and a vision Dataset inside real torch.utils.data.DataLoaders, and the real 2-hop GNN sampler — fed synthetic corpora. Real-case loader layout: 8 DataLoader ranks per node (one per GPU, as torchrun runs), each with num_workers=4; shards owned per node (1× partitioning), ranks read disjoint slices. Access is random (the shuffled-sample pattern of real training). Speedup = native epoch wall ÷ FitCachePP-warm epoch wall of the same loader run (slowest rank = epoch). Every scale is measured with a cold native: each runs as the first reader of its corpus after an ≥8.5 h cool-down (one scale per slot). The two sides move oppositely: the warm epoch stays nearly flat (0.7 s → 3.7 s; all I/O is node-local NVMe), while the cold-Lustre native epoch is large and grows noisy with concurrent-reader contention (21 s → 145 s across scales; hundreds-to-thousands of ranks issuing random small reads against the shared PFS). Speedup therefore tracks Lustre's contention behavior, not a cache limitation — exactly the Tpfs-contention regime of the performance model. This is the headline scaling result: FitCache++ turns a contended shared-PFS workload into a scale-invariant node-local one.

(1) Access pattern decides the win: random/latency-bound access gains 5–30×; sequential scans gain ~nothing on Orion (Lustre seq ≈ NVMe seq) — why the old sequential benches were retired. (2) 1× vs N× is the storage story: sample-partitionable workloads hold the corpus once cluster-wide at every scale; GNN's data-dependent gather forces N×. (3) The cache scales; what fades at scale is either the need (slices fall into RAM) or the surroundings (loader ceiling, node SSD class) — quantified in §1.5. (4) Strong vs weak scaling separates the two regimes cleanly: with a fixed corpus the benefit correctly fades once per-node slices fit in RAM (§1.1); with the dataset growing with the machine — the realistic large-training regime — the benefit is sustained at every scale to 2048 GPUs (§1.1b).

1.5 — Method notes & caveats

Cold baselines. A native measurement is only “cold” if it is the first reader of the corpus after an ≥8.5 h cool-down (Lustre's servers cache recently-read data). Every speedup in §1.1–1.2 is measured that way, one scale per slot; GNN (§1.3) uses 39-day-aged data + page-cache eviction. Cold points are single-shot (a cold measurement consumes its own coldness).
Node-SSD variance. Frontier nodes have two SSD speed classes (~1.9 vs ~5 GB/s direct-read); random-access warm reads are slower on the majority class, and the epoch metric (slowest rank) includes the slowest node. This is a property of node-local storage, not of FitCachePP — worth one discussion paragraph in the paper.
Footprints are exact 1/N. Byte-exact cache census (no growth through warm) and du-verified series (515G→4.0G, 1.0T→8.0G). Table values are per-node du from each run.
Synthetic bytes, real loaders. The benchmark measures the access pattern of real loader code; Megatron reads through its real .idx. Client fixes shipped during the campaign (local warm resolve without PFS stat; open-RPC skip when cached; fstat coverage guard) — warm-path correctness verified at scale: 100% cache hits, zero fallbacks.

Part 2 — Design-feature validations

Part 1 measures the whole system; Part 2 validates the individual design features the system relies on — restart resilience via .meta recovery, and tier generality of the cache path — each with its own measured result. (Design rationale: design.html; code: implementation_walkthrough.html.)

2.1 — Restart resilience: server-independent warm path + .meta recovery RE-VERIFIED 2026-07-07

Design feature: training must survive a cache-service crash/restart. Two layers provide it: the client warm path never depends on server state (deterministic resolve + local verification), and the server rebuilds its bookkeeping from .meta sidecars on startup. Restart test (kill the cache service mid-run, restart, continue the loader):

MeasureResult
Warm mmaps after service kill + restart32/32 (100%), zero native fallbacks
Warm read bandwidth across the restart2.4 GB/s (unchanged)
Loader stall on restartNone — client resolves and verifies against the cached files themselves
Warm-path .meta use (2026-07 client)Sidecar consulted when present: size + original-path verification on the hot path

Scope (honest): the prefetch/populate path used by the headline experiments lands cached shards without .meta files (measured: 31 shards cached, 0 sidecars), so server-side restore_from_sidecars currently rebuilds bookkeeping only for shards promoted through the on-demand (open-triggered) path, which writes sidecars. The earlier restore-count/time tables (old workloads through that path) are retired. Open decision: have the populate path write sidecars too (small server-side change → full recovery coverage), or keep the recovery claim scoped to on-demand-promoted data. Client-side warm correctness across restart holds either way, as measured above.

2.2 — Tier generality: DRAM (tmpfs) vs NVMe DONE

Design feature: the cache path is tier-general — the data mover places by remaining capacity (DRAM/tmpfs → PMem → NVMe) and the resolver probes the same order, so the mechanism is a tiered node-local cache, not an NVMe-only cache.

Why NVMe backs the headline: the DRAM datapoint is a cold-start regime — once a working set fits tmpfs, the native baseline page-caches it too and the sustained gap washes out (same-RAM-pages argument, walkthrough §3b). NVMe is the tier where the >RAM working sets that need the cache actually live.
