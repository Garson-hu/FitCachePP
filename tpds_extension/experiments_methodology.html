FitCachePP — Experiments Methodology

This page explains how each experiment is built, run, and measured — the datasets, the access pattern that stands in for a real model, and the exact run procedure. It is about method, not results; every claim points to a file:line in the repo so you can check it. Companion pages: EXPERIMENTS_STATUS.html · experiments.html · implementation_walkthrough.html.

Every benchmark measures one thing: how fast can a job read its data? The bytes come from one of three tiers, fastest to slowest — node RAM (page cache), node-local fast disk (NVMe / tmpfs), or the shared Lustre filesystem over the network. FitCachePP transparently moves a file from slow Lustre to a fast local copy and serves reads from there.

2. Glossary

Keep the three-layer picture above in mind. These are I/O benchmarks: there is no neural network, no forward or backward pass. In place of a model we run a fixed, repeatable access pattern and then touch every byte we read (add it into a running sum) so the read genuinely happens and cannot be optimized away. With that in mind, here is what each recurring term means:

TermWhat it actually means
cold (the native baseline)Reading a file for the first time when none of it is in RAM yet. For the Native_mmap_PFS baseline this means the bytes come straight from Lustre over the network. We force this condition by flushing RAM first (§3.4). This is the line everything else is compared against.
warm-hit-prestagedFitCachePP's first pass over the data. We copied the file to fast local storage before timing started, so even the first read comes from local NVMe or tmpfs instead of Lustre. In other words: it is the first epoch in time, but it already behaves like a cache hit because the copy is waiting. The logs tag it warm-hit-prestaged.
warm (page-cache resident)The second and later passes over the same bytes, when the OS has already kept them in RAM from the previous pass. This is the operating system's own caching and it helps both FitCachePP and the native baseline equally — so it is not a FitCachePP effect.
amortizedThe honest total: time across all passes including the one-time cost of copying the data to local storage. We report it as "after how many passes does FitCachePP come out ahead?" (see §3.6) so the staging cost is never swept under the rug.
regime-pinnedA deliberately fair setup: we make each node's data bigger than the node's RAM (e.g. 640 GiB of data on a 512 GiB node). Then neither side can secretly serve reads from RAM — every pass really hits a storage tier. This stops a "looks fast but it was just RAM cache" illusion.
checksum gateThe correctness check. FitCachePP and the native baseline must read back the exact same bytes (identical checksum, on every rank), or the result is thrown out. This guarantees the speedup is real and not from reading less or wrong data.

3. Common experimental machinery

Every workload reuses the same building blocks. This section explains each one once.

3.1 Server launch & rendezvous

The FitCache servers run as their own background job step next to the benchmark. Each node runs 4 of them, so a run on N nodes has N×4 servers. When they start, they write their network addresses into a small file (.ports.cfg.$SLURM_JOBID); the client reads that file to find them.

# servers (backgrounded), then the benchmark step
srun -N $N_NODES -n $TOTAL_SERVERS --ntasks-per-node=$SERVERS_PER_NODE \
     --cpus-per-task=1 --cpu-bind=cores "$FITPP_SERVER_BIN" $TOTAL_SERVERS \
     > "$RESULTS_DIR/server.log" 2>&1 &
sleep 15                       # readiness (older scripts); scale-ladder polls the port-cfg file instead

scripts/frontier/frontier_sidecar_recovery.sh:136-139 · scale-ladder job.sh polls port-cfg (harness fix)

One subtlety worth stating: on the warm-hit measurements the servers are not even on the read path. A warm hit is resolved entirely by the client (it figures out the local copy's location itself and mmaps it — see §4–§6). We still run the servers so the open/promotion path stays realistic, but the read speed does not depend on them.

3.2 Tier configuration & the deterministic hash-bin path

Two local tiers are set via environment variables, and we tune their capacities per experiment. A common trick: set the DRAM tier's capacity tiny on purpose, which forces files to land on NVMe instead (and vice-versa when we want to prove the DRAM path).

export FitCache_DRAM_PATH=/tmp/fitcachepp_<tag>_dram          # tmpfs (RAM-backed)
export FitCache_NVME_PATH=/mnt/bb/$USER/fitcachepp_<tag>_nvme  # burst-buffer NVMe
export FitCache_DRAM_CAPACITY=$((256*1024*1024))             # e.g. 256 MiB -> forces NVMe tier
export FitCache_NVME_CAPACITY=$((2000*1024*1024*1024))       # e.g. 2 TB
export FitCache_LOG_LEVEL=600    # verbose server logging
export FitCache_CROSS_JOB=0      # single-job mode for all reported experiments

The key design point: the server (which copies files in) and the client (which looks them up) both compute the same cached filename from the original path, using the same hash. So the client can find a pre-staged copy on its own, with no network round-trip to ask "where is this file?". The naming scheme:

// tools/fitcache_cached_path.cpp:14-19
size_t h = std::hash<std::string>(original_path);
subdir   = sprintf("%02zx/%02zx", (h >> 8) & 0xFF, h & 0xFF);
cached   = tier_base + "/" + subdir + "/" + basename(original_path);

3.3 Pre-staging (warm-hit setup)

To measure a warm hit, we first copy the files each node will read into that node's local tier, putting them at exactly the filename the client's resolver expects (using the fitcache_cached_path tool). We time this copy separately and never count it as a read epoch.

dst=$("$FITPP_REPO/tools/fitcache_cached_path" "$src" "$FitCache_NVME_PATH")
mkdir -p "$(dirname "$dst")"
if [ ! -f "$dst" ] || [ "$(stat -c %s "$dst")" != "$(stat -c %s "$src")" ]; then
  cp "$src" "$dst"        # whole-file copy; resolver gate is a full-size match
fi

frontier_megatron_warmhit_sweep.sh:75-86 · frontier_gnn_warmhit_sweep.sh:98-102

The acceptance test is "right size," not "right contents." When the client decides whether a local copy is usable, it checks only that the file exists and its size matches the original — there is no per-file content hash at staging time. A corrupted same-size copy would slip past this check, but it would still be caught at the end by the checksum gate (§3.5), which compares the actual bytes read against the native baseline.

3.4 Page-cache eviction (enforcing "cold")

To measure a genuine cold read, we first have to kick the data out of RAM — otherwise the OS would quietly serve it from the page cache and the "cold" number would be fake. We do this with a memory-pressure tool, mem_hog.c: it allocates a big chunk of anonymous memory and touches every 4 KiB page, which forces the kernel to evict the file-backed pages to make room. A bounded loop watches Cached: in /proc/meminfo and keeps hogging until it drops below a threshold.

evict_all() {  # scale-ladder, per node, before each rep
  srun --overlap -N $N -n $N --ntasks-per-node=1 --cpus-per-task=16 bash -c '
    for pass in 1 2 3 4 5; do
      cached_gb=$(awk "/^Cached:/{printf \"%d\", \$2/1048576}" /proc/meminfo)
      [ $cached_gb -le 8 ] && break        # target: Cached <= 8 GB
      hog=$((cached_gb+30)); per=$(( (hog+7)/8 ))
      for i in 1 2 3 4 5 6 7 8; do "$RESULTS_DIR/mem_hog" $per 1 >/dev/null 2>&1 & done; wait
    done'
}

megatron_scale_ladder/…/job.sh:43-59 · gnn_regime_pinned/…/job.sh:44-64 · benchmarks/util/mem_hog.c:64 · (older scripts also use posix_fadvise(POSIX_FADV_DONTNEED): frontier_llm_dataloader_compare.sh:107-120)

Eviction is best-effort, and we say so. On a 512 GiB node with a small working set (the GNN gather touches only ~2.67 GB), mem_hog sometimes cannot flush everything. So for GNN we treat rep 1 (the cleanest eviction) as the anchor result and keep reps 2–3 (which kept some data in RAM) only to show run-to-run spread. Anyone reproducing this should check /proc/meminfo to confirm how cold the run really was.

3.5 The checksum-equality gate (correctness)

This is how we prove the speedup is honest. Every benchmark adds up the bytes it reads into a GLOBAL_CHECKSUM, one per rank. The harness then compares the full set of per-rank checksums (not just rank 0) between FitCachePP and the native baseline. If they are not identical, the result is a FAIL.

pairs() { grep 'SUMMARY' "$1" | sed -nE 's/.*rank=([0-9]+).*GLOBAL_CHECKSUM=([0-9]+).*/\1=\2/p' | sort -n; }
if [ "$(pairs native.log)" = "$(pairs fitcachepp.log)" ]; then echo "CHECKSUM_GATE: PASS"; else echo FAIL; fi

frontier_gnn_warmhit_sweep.sh:159-173 · frontier_megatron_warmhit_sweep.sh:127-132

The exact byte-touch differs a little by workload, but each reduces to a 64-bit integer so it cannot overflow on TB-scale runs: Megatron sums a uint16 view; GNN sums a uint32 view masked to 63 bits; DINOv2 sums a uint8 view masked to 63 bits. Both sides use the same view, so a match is exact. llm_coverage_bench.py:100 · gnn_feature_bench.py:198 · cc12m_mmap_bench.py:170

3.6 Two-view reporting (mechanism vs. amortized)

We always report the speed two ways, so the one-time staging cost is visible:

  • View 1 — the mechanism alone: warm epoch vs. native epoch. This isolates the benefit of reading from the local tier instead of Lustre, ignoring setup cost.
  • View 2 — the honest total: include the one-time pre-stage copy and ask after how many epochs E FitCachePP wins overall, i.e. when pre_stage + E·warm < E·cold. We report this break-even at E = 1…5.

frontier_dinov2_warmhit_sweep.sh:135-147

What stands in for the "model"

Why "no model"? A real Megatron run does three things per step: (1) read tokens from disk, (2) run them through the neural network on the GPU (the expensive forward/backward pass), (3) update the model's weights. We only want to measure step (1), the reading — step (2) is heavy GPU compute that overlaps with I/O and would make the read time impossible to isolate. So instead of a real model we run a small benchmark, llm_coverage_bench.py, that does only the reading: it reproduces exactly how a real loader would touch the file, but skips the neural network entirely. "The driver is llm_coverage_bench.py" just means this script — not a real LLM — is what drives the experiment.

What it does: it mmaps each shard and reads a --coverage fraction of it, spread evenly across the shard in --n-chunks contiguous pieces, adding the bytes into GLOBAL_CHECKSUM (the sum both forces the read to really happen and serves as the correctness check). On multiple nodes the shards are split round-robin (rank R of N reads shards [R, R+N, R+2N, …]) so every node does equal work. (A second driver, llm_dataloader_bench_sharded.py, instead reads random sequences via IndexedDataset.get(doc, length=seq_length); the warm-hit sweep uses the coverage bench.)

5. Workload 2 — GNN feature gather (sparse-random, IGB-large)

A graph-learning data loader. It reads a few thousand tiny, scattered feature rows from a huge file — the worst case for Lustre, so this is where FitCachePP wins biggest on the warm hit. This is also the un-partitionable workload: the 2-hop heterogeneous gather can touch any feature row (the access set is data-dependent, not a contiguous slice), so unlike Megatron and DINOv2 it cannot prefetch only a 1/N partition — every node must hold the whole feature+CSR set (902 GB) and storage stays N×. Prefetch still earns the warm local hit; it just cannot earn the 1× storage win here (see §7).

Dataset & format

WhatThe real IGB-large academic graph: 100 M paper nodes, 116.96 M author nodes, 2 relations (paper_cites_paper, paper_written_by_author).
FormatNode features are raw float32 numpy arrays — paper_node_feat.npy shape (100 M, 1024) and author_node_feat.npy shape (116.96 M, 1024). Each row is 1024×4 = 4096 B, exactly one page. The graph itself is stored as CSR (int64 indptr + indices).

What stands in for the "model"

The "model" is a 2-hop graph sampler that drives a sparse feature gather — there are no GNN layers and no training, just the data access a real sampler would generate:

  1. Pick 1024 random seed papers (hop 0).
  2. Hop 1: sample up to 12 paper→paper neighbours and up to 8 paper→author neighbours (--fanout-pp 12 --fanout-pa 8).
  3. Hop 2: sample up to 8 more paper→paper neighbours of the hop-1 papers (capped at 4096) (--fanout-pp2 8).
  4. Collect the unique paper + author rows touched, then gather them block by block: split the rows into 12 GiB blocks (3,145,728 rows), mmap each block by offset, pull its rows, and sum the uint32 view into the masked checksum.

This touches only ~2.67 GB (~0.3%) of the 902 GB corpus — exactly the small, random, scattered reads that crawl on Lustre. Each epoch is 20 batches × 1024 seed papers.

The two sides are not symmetric — on purpose, and stated openly. We compare "FitCachePP reading its local copy (warm-hit-prestaged)" against "the native app reading cold from Lustre (separately evicted)." That is not a warm-vs-warm race; it is the actual question we care about — local fast tier vs. the shared filesystem. The checksum gate proves both sides read identical bytes, so the comparison is fair even though the starting conditions differ.

What stands in for the "model"

The unit of work is a "shard pass," not a full-corpus epoch. 7. Whole-system method — prefetch-informed migration & 1× partitioning

The whole system is the transparent mmap cache path (§3–§6) plus one extra hint the application gives ahead of each read: prefetch-informed migration. Instead of every node pre-staging the entire corpus (replicate-all, which costs N× the dataset cluster-wide), the cluster keeps a file cached once and migrates that single copy to whichever node is about to read it, ahead of the read and overlapped with the current epoch's compute. Each node therefore prefetches only its own 1/N partition, the cluster holds the read set once (1×), and every read is still a warm local mmap.

Why a hint is load-bearing on Frontier. Frontier has no NVMe-oF / remote DAX, so a node cannot mmap a peer's NVMe directly. "Migration" here is a whole-file network transfer that lands the copy in the requesting node's local tier. Done lazily at mmap time it is no better than the existing per-read RPC fallback — the read still waits on the network. It only pays off when the file is prefetched, so the transfer overlaps with compute and the data is already local when the read arrives. That is why the application declares its files up front rather than letting the cache fill reactively.

7.1 The fitcache_prefetch hint and the peer→local migrate

The application declares the files it is about to mmap through a new C API, fitcache_prefetch(path, replication_mode). The call is exported from the client library and reachable through the same LD_PRELOAD shim as the mmap interceptors, so no application source change is required beyond the one hint. It issues a prefetch RPC to the owning server, which enqueues the work at PREFETCH priority and runs the crux primitive — a single bulk peer→local whole-file transfer (not the per-pread loop) that lands the copy exactly like a PFS promote (hash-bin path + cache map + .meta file + presence broadcast).

7.2 replication_mode — how many copies the cluster keeps

The second argument selects the replication policy; the chosen replication_mode (and a replication_cap for the bounded case) is forwarded through the RPC and recorded in each cached file's .meta file (src/cross_job/fitcache_persistent_meta.h), so the policy survives a server restart.

ModeValueWhat it means
SINGLE_COPY1One copy cluster-wide; migrate peer→local on demand. This is the 1× policy the partitionable workloads use.
BOUNDED_K2At most k copies (replication_cap), for hot / concurrently-read files.
UNBOUNDED0The old replicate-all default — every node keeps its own copy (N×).

7.3 How each node prefetches its 1/N partition, and how 1× is confirmed

For the two partitionable workloads each rank declares only its disjoint slice before reading it: rank R of N prefetches the shards it owns (Megatron round-robin [R, R+N, …]; DINOv2 its disjoint shard range), issued via the fitcache_prefetch_shim.py ctypes wrapper. Because no node ever fetches a peer's slice, the union of all per-node local copies is exactly one copy of the read set. We confirm the 1× footprint with du on each node's NVMe tier: each node's cached bytes equal its partition (Megatron 32/N shards × 16 GiB, DINOv2 its shard set), so the cluster total is 1× the dataset rather than replicate-all's N×.

GNN stays un-partitionable. The 2-hop heterogeneous gather can touch any feature row, so its access set is not a contiguous slice; every node must hold the whole feature+CSR set (902 GB) and storage stays N×. Prefetch still earns the warm local hit there — it just cannot earn the 1× storage win.

8. Whole-system result — prefetch 1× study at two scales (1–16 and 32–256 nodes)

The whole-system study runs the mmap cache path + prefetch at two scales and asks two things together: does the warm local read hold as the job grows, and does the cluster footprint stay at 1×. Megatron (dense-sequential) and DINOv2 (sequential vision) are the 1×-partitionable cases; GNN is the un-partitionable column (warm hit only, storage N×). The two ranges 1–16 and 32–256 use the same binary and method so they join into one curve. Numbers are authoritative in experiments.html §1.1–§1.2; this section defines how they are produced and what each metric means.

  • Setup per rank: the rank declares its 1/N partition via fitcache_prefetch (SINGLE_COPY), which migrates that slice peer→local overlapped with compute; the rank then mmap-reads it warm.
  • Per rep: a mem_hog eviction on all nodes before timing, so the cold-side read is genuinely cold.
  • Arms (warm first): FitCachePP warm epoch vs. Native_mmap_PFS; the native cold epoch is run last so a native timeout at scale still preserves the warm result.
  • Every step uses srun --overlap to avoid a step-creation deadlock with the backgrounded server step.

10. Ablation — recovery from .meta files (4 phases)

This ablation isolates the recovery mechanism: does the cache survive a server restart, and what specifically does the .meta file buy? Each cached file gets a small .meta file recording what it is; when a server restarts, it reads those .meta files to rebuild its memory of what is already cached, so the next run warm-hits instead of re-fetching from Lustre. (We isolate the mechanism here and add a no-.meta-file arm for comparison.) Driven by frontier_sidecar_recovery.sh for any of the three workloads (BENCH=megatron|gnn|dinov2), in four phases:

  1. P1 Populate: bring up server #1 and run a cold epoch — reading a file triggers a promotion that copies it to the local tier and writes its .meta file.
  2. P2 Kill: kill server #1 and wipe the port-cfg file (simulating a crash/restart).
  3. P3 Restart: bring up server #2; restore_from_sidecars scans the tier directories and rebuilds the cache map. The harness waits (≤120 s) until the server log reports total restored = N.
  4. P4 Post-restart pass: re-run the benchmark over the same paths; a probe confirms every file warm-hits (hit==expected, fallback==0), and the checksum must match the populate phase (both run --epochs 2 so the raw checksums are comparable).

A SKIP_POST=1 variant measures restore time only (the restore-scaling sweep over 32 / 256 / 996 objects).

11. Methodological honesty & known limitations

Stated plainly, so the method is reproducible and nobody over-reads the numbers:

  • The two sides start from different states — on purpose. FitCachePP's timed epoch is a warm read of a local copy; the native baseline is a cold read from Lustre (separately evicted). That is the question we are asking — local tier vs. shared filesystem — and the checksum gate proves identical bytes. It is not a warm-vs-warm comparison, and we never present it as one.
  • Eviction is best-effort. On a 512 GiB node with a small working set (GNN ~2.67 GB), mem_hog cannot fully flush RAM, so the GNN headline uses rep 1 (cleanest eviction) as the anchor and keeps reps 2–3 only as variance context.
  • Native Lustre speed depends on cluster conditions. The same native cold epoch varies with time-of-day contention (e.g. the GNN cold gather swings from ~4419 s to ~827 s across node counts). The warm side is the stable quantity, so the honest framing for the un-partitionable GNN column is warm-flat + native-volatile, not a fixed speedup that grows with scale.
  • The GNN pooled checksum gate is "cosmetically" failed by design, but the data is verified correct. The pooled gate takes a set-union of per-rank checksums across ranks that each sample different random rows, so it reports N distinct values; the per-rank gate confirms warm == native byte-for-byte at every rung (256/256 ranks at N=256). The per-rank check is the real integrity test and it passes.
  • The staging check is size-only, not a content hash (§3.3) — integrity ultimately rests on the end-to-end checksum gate.
  • At 1× the per-node partition fits node RAM, so the warm→warm number is small by construction: after one pass the native baseline page-caches its slice too, and the only durable benefit is the cold→warm gap. We report warm→warm anyway rather than hide it. (The un-partitionable GNN case keeps the whole 902 GB set per node, larger than RAM, so its native cold gather genuinely hits Lustre every time.)
  • These are data-loading I/O benchmarks. The "model" is a fixed access pattern plus a byte-touch, not a real forward/backward pass. All claims are scoped to mmap-backed data loading, not end-to-end training.
  • The one-time staging cost is reported separately and only folded back into the amortized (View 2) break-even — it is never hidden inside a warm epoch.

12. 2026-06 re-measurement — real loaders, concurrency, cold-native protocol

This section defines the method behind the current headline tables (experiments.html Part 1). It supersedes the measurement method of §4 (Megatron sequential bench), §6 (DINOv2 sequential tar), and §8 (serial 1-rank ladder); the platform (§1), tier/hash-bin machinery (§3), and GNN harness (§5) carry over.

12.1 Design rules

  • Real workload, synthetic data. The data-loading code path is the real one; only the bytes are synthetic. Megatron: megatron.core.datasets.indexed_dataset.IndexedDataset (real .idx + mmap .bin) wrapped in torch.utils.data.DataLoader(num_workers=8, prefetch_factor=4) (benchmarks/megatron/megatron_dataloader_bench.py). Vision: a Dataset that mmaps one random 150,528-byte record (3×224×224 uint8) per sample, in the same real DataLoader (benchmarks/vision/vision_dataloader_bench.py; returns uint8 — the normalize-on-GPU convention). GNN: the §5 harness unchanged — real IGB CSR, real 2-hop heterogeneous sampling.
  • Concurrency mirrors 8 GPUs/node: 8 loader workers (Megatron/Vision) or 8 gatherer ranks (GNN) per node. Serial single-rank numbers are upper bounds and are no longer reported.
  • Random access only. Shuffled-sample reads are what training issues; they are latency/IOPS-bound, where the NVMe tier wins. Sequential scans are bandwidth-bound (Orion Lustre seq ≈ node NVMe seq) and cannot show the cache win — the reason the old §4/§6 sequential benches were retired.
  • Metric: speedup = native epoch wall / FitCachePP-warm epoch wall of the same loader run (slowest rank = epoch time). Both arms execute identical code; only the byte source differs (Lustre vs node-local NVMe).

12.2 Corpora & 1× partition

  • Megatron: synth_1tb_256x4gb — 256 × 4 GiB shards + real .idx (1 TiB).
  • Vision: synth_2tb_256x8gb_img — 256 × 8 GiB shards of fixed 150,528-B records (2 TiB, ~14.6 M images), generated by benchmarks/vision/generate_synth_img_corpus.py.
  • Partition: node i of N owns shards [i·256/N, (i+1)·256/N) — whole files, disjoint, union = one copy → 1× cluster storage, du-verified per node at every scale. 256 shards ⇒ clean 1× to 256 nodes (2048 GPUs). GNN is un-partitionable (any row reachable) ⇒ whole 841 GiB set per node, N× by design.

12.3 Cold-native protocol (OST-cache confound)

A freshly written corpus is hot in Lustre's server-side (OST) cache, so a naive “native” run reads warm Lustre and understates nothing but overstates native speed → deflated speedups. Protocol: (a) ≥8 h cool-down between corpus writes/populates and native measurement (Megatron/Vision); (b) GNN uses 39-day-aged data + mem_hog page-cache eviction (§3) before every arm; (c) within a shared-corpus sweep, only the first scale to run (N=2) is guaranteed true-cold — later scales read partially OST-warmed data, so their speedups are lower bounds. Single-shot cold points: a cold measurement consumes its own coldness, so cold runs are not repeated back-to-back.

12.4 Run shape

Per scale N (launchers run_megatron_dl.sh / run_vision_dl.sh / run_gnn_rand_job.sh): STEP 1 native (no LD_PRELOAD, Lustre) → start 1 server/node → STEP 2 populate (sequential coverage read under FITCACHE_PREFETCH=1, promotes whole shards; poll per-node du until the partition is resident) → STEP 3 warm (same loader, LD_PRELOAD, node-local NVMe) → per-node du footprint. Single-job mode FitCache_CROSS_JOB=0, FITCACHE_MMAP_PLACEMENT=node_local, FitCache_HEARTBEAT_SEC=120.

12.5 Client fixes required at scale (2026-06-29 → 07-06, src/client/)

  • fitcache_resolve_cached_path: warm-hit completeness now verified locally (cached file present — it lands via atomic rename — and its size matches the .meta file's recorded original_size). Previously each mmap issued a Lustre stat(original_path): one MDS round-trip per record, a metadata storm at 1–2k ranks.
  • fitcache_track_file: std::filesystem::canonical(path) (a Lustre realpath) computed once per open (was 3–4×) and the constant canonical(data_dir) cached process-wide.
  • Open path: the fire-and-forget open RPC is skipped when the file already resolves to a complete local copy (its only job is to trigger promotion).
  • fstat coverage guard (mmap wrapper): before mapping a cached file, fstat must show it covers the requested [offset, offset+length); otherwise fall back to the native PFS mmap. A short or still-growing copy can no longer SIGBUS a reader — this closed an 8-rank promotion race (bus errors at every rank, 2026-07-05).
  • .meta check is optional-when-present: the prefetch/populate path lands complete cached files without sidecars, so requiring a sidecar (tried 2026-07-06 as a stronger gate) silently turned every populated file into a resolve miss and sent all “warm” reads back to Lustre. Now: sidecar present → size + original-path must match (stale/collision protection); sidecar absent → accept, protected by the fstat guard.

12.6 Known ceiling — the Python DataLoader, not the cache

With identical cached data at N=64/128, an 8-process mp.Pool reader over the same mmap path sustains ~10 GB/s per node warm (scale-flat), while torch.utils.data.DataLoader saturates at ~0.1–0.3 GB/s — its single-threaded main process consuming worker tensors is the ceiling (verified: uint8 vs float32 and per-sample vs pre-batched IterableDataset variants all hit the same cap; see benchmarks/results/frontier/VISION_SCALE_CAMPAIGN.md). Consequence: for large-record workloads the end-to-end loader speedup fades once the loader ceiling drops below native Lustre speed (Vision N≥64), even though the storage-tier speedup persists. Claims are therefore split: end-to-end loader speedup (conservative, includes the framework) vs I/O-path speedup (the access-pattern reader).

12.7 Real-case loader layout — 8 ranks/node (2026-07-05→07)

The §12.1 runs use one DataLoader rank per node (a single main-process consumer for the whole node — a pessimistic bound, per §12.6). The real-case layer re-measures the two 1× workloads in the layout real torchrun training uses: 8 ranks per node (one per GPU), each with its own DataLoader(num_workers=4, prefetch_factor=2) — 8 consumers + 32 workers per node (srun --ntasks-per-node=8 --cpus-per-task=7). Shard ownership stays per node (SLURM_NODEID selects the shard slice → 1× partitioning unchanged); the node's local ranks take disjoint strided slices of the same per-node sample plan (plan[SLURM_LOCALID::8]), so bytes/node match the 1-consumer runs exactly and the two layouts are directly comparable. Launchers run_vision_dl8.sh / run_megatron_dl8.sh; results in REAL_CASE_TABLES_v2.txt (experiments.html §1.0). Native-side effect: 32 Lustre streams/node instead of 8 (more contention at scale — the honest configuration). Known open items (2026-07-07, under diagnosis): partial warm fallback at Vision N≥8 (bimodal per-rank walls) and re-promote-driven du inflation during warm; the exact-1× footprint evidence remains the 1-consumer ladder.
