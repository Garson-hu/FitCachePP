FitCachePP — Experiments Methodology

This page explains how each experiment is built, run, and measured — the datasets, the access pattern that stands in for a real model, and the exact run procedure. It is about method, not results; every claim points to a file:line in the repo so you can check it. Companion pages: EXPERIMENTS_STATUS.html · experiments.html · implementation_walkthrough.html.

The one idea behind every experiment. All of these benchmarks measure one thing: how fast can a job read its data? The same bytes can come from one of three places, fastest to slowest — (1) the node's RAM (the OS "page cache," nanoseconds), (2) the node's local fast disk (NVMe burst buffer or a RAM-backed tmpfs, microseconds), or (3) the shared Lustre filesystem over the network (milliseconds, and far worse for tiny scattered reads). FitCachePP's whole job is to quietly move a file from slow Lustre to a fast local copy and serve reads from there, without the application noticing. So every term below is really just answering: on this particular read, which of the three layers did the bytes come from, and who paid to put them there?

2. Glossary

Keep the three-layer picture above in mind. These are I/O benchmarks: there is no neural network, no forward or backward pass. In place of a model we run a fixed, repeatable access pattern and then touch every byte we read (add it into a running sum) so the read genuinely happens and cannot be optimized away. With that in mind, here is what each recurring term means:

TermWhat it actually means
cold (the native baseline)Reading a file for the first time when none of it is in RAM yet. For the Native_mmap_PFS baseline this means the bytes come straight from Lustre over the network. We force this condition by flushing RAM first (§3.4). This is the line everything else is compared against.
warm-hit-prestagedFitCachePP's first pass over the data. We copied the file to fast local storage before timing started, so even the first read comes from local NVMe or tmpfs instead of Lustre. In other words: it is the first epoch in time, but it already behaves like a cache hit because the copy is waiting. The logs tag it warm-hit-prestaged.
warm (page-cache resident)The second and later passes over the same bytes, when the OS has already kept them in RAM from the previous pass. This is the operating system's own caching and it helps both FitCachePP and the native baseline equally — so it is not a FitCachePP effect.
amortizedThe honest total: time across all passes including the one-time cost of copying the data to local storage. We report it as "after how many passes does FitCachePP come out ahead?" (see §3.6) so the staging cost is never swept under the rug.
regime-pinnedA deliberately fair setup: we make each node's data bigger than the node's RAM (e.g. 640 GiB of data on a 512 GiB node). Then neither side can secretly serve reads from RAM — every pass really hits a storage tier. This stops a "looks fast but it was just RAM cache" illusion.
checksum gateThe correctness check. FitCachePP and the native baseline must read back the exact same bytes (identical checksum, on every rank), or the result is thrown out. This guarantees the speedup is real and not from reading less or wrong data.

2.1 A few base terms (assume nothing)

The workload sections below use a handful of words from machine learning and operating systems. If any of them are unfamiliar, here is the plain version:

TermPlain meaning
mmap (memory-map)A way to read a file without calling read(). The program asks the OS to "pretend this file is an array in memory"; then, the first time it touches any part of that array, the OS quietly fetches the corresponding bytes from disk (a "page fault"). Modern data loaders use this because it is simple and avoids copying. It also matters here because those page-fault reads are invisible to a normal read()-based cache — which is the whole gap FitCachePP closes.
epoch / passOne complete sweep over the dataset. Training does many epochs; here we run 2–3 so we can see the first (cold) pass and a later (warm, already-in-RAM) pass.
token / tokenizeA language model does not read text; it reads integers. A "tokenizer" chops text into small pieces ("tokens") and maps each to an integer ID (e.g. "cat" → 1842). A training corpus is stored as one long stream of these integer IDs.
rankOne worker process in a parallel job. A run on N nodes with 1 worker each has N ranks; each rank reads its own slice of the data.
shardThe dataset split into many separate files so it can be read in parallel. "40 shards" = 40 files.
working setThe amount of data a node actually reads in one pass. We compare it against the node's 512 GiB RAM to know whether reads can hide in the OS cache.

3. Common experimental machinery

Every workload reuses the same building blocks. This section explains each one once.

3.1 Server launch & rendezvous

The FitCache servers run as their own background job step next to the benchmark. Each node runs 4 of them, so a run on N nodes has N×4 servers. When they start, they write their network addresses into a small file (.ports.cfg.$SLURM_JOBID); the client reads that file to find them.

# servers (backgrounded), then the benchmark step
srun -N $N_NODES -n $TOTAL_SERVERS --ntasks-per-node=$SERVERS_PER_NODE \
     --cpus-per-task=1 --cpu-bind=cores "$FITPP_SERVER_BIN" $TOTAL_SERVERS \
     > "$RESULTS_DIR/server.log" 2>&1 &
sleep 15                       # readiness (older scripts); scale-ladder polls the port-cfg file instead

scripts/frontier/frontier_sidecar_recovery.sh:136-139 · scale-ladder job.sh polls port-cfg (harness fix)

One subtlety worth stating: on the warm-hit measurements the servers are not even on the read path. A warm hit is resolved entirely by the client (it figures out the local copy's location itself and mmaps it — see §4–§6). We still run the servers so the open/promotion path stays realistic, but the read speed does not depend on them.

3.2 Tier configuration & the deterministic hash-bin path

Two local tiers are set via environment variables, and we tune their capacities per experiment. A common trick: set the DRAM tier's capacity tiny on purpose, which forces files to land on NVMe instead (and vice-versa when we want to prove the DRAM path).

export FitCache_DRAM_PATH=/tmp/fitcachepp_<tag>_dram          # tmpfs (RAM-backed)
export FitCache_NVME_PATH=/mnt/bb/$USER/fitcachepp_<tag>_nvme  # burst-buffer NVMe
export FitCache_DRAM_CAPACITY=$((256*1024*1024))             # e.g. 256 MiB -> forces NVMe tier
export FitCache_NVME_CAPACITY=$((2000*1024*1024*1024))       # e.g. 2 TB
export FitCache_LOG_LEVEL=600    # verbose server logging
export FitCache_CROSS_JOB=0      # single-job mode for all reported experiments

The key design point: the server (which copies files in) and the client (which looks them up) both compute the same cached filename from the original path, using the same hash. So the client can find a pre-staged copy on its own, with no network round-trip to ask "where is this file?". The naming scheme:

// tools/fitcache_cached_path.cpp:14-19
size_t h = std::hash<std::string>(original_path);
subdir   = sprintf("%02zx/%02zx", (h >> 8) & 0xFF, h & 0xFF);
cached   = tier_base + "/" + subdir + "/" + basename(original_path);

3.3 Pre-staging (warm-hit setup)

To measure a warm hit, we first copy the files each node will read into that node's local tier, putting them at exactly the filename the client's resolver expects (using the fitcache_cached_path tool). We time this copy separately and never count it as a read epoch.

dst=$("$FITPP_REPO/tools/fitcache_cached_path" "$src" "$FitCache_NVME_PATH")
mkdir -p "$(dirname "$dst")"
if [ ! -f "$dst" ] || [ "$(stat -c %s "$dst")" != "$(stat -c %s "$src")" ]; then
  cp "$src" "$dst"        # whole-file copy; resolver gate is a full-size match
fi

frontier_megatron_warmhit_sweep.sh:75-86 · frontier_gnn_warmhit_sweep.sh:98-102

The acceptance test is "right size," not "right contents." When the client decides whether a local copy is usable, it checks only that the file exists and its size matches the original — there is no per-file content hash at staging time. A corrupted same-size copy would slip past this check, but it would still be caught at the end by the checksum gate (§3.5), which compares the actual bytes read against the native baseline.

3.4 Page-cache eviction (enforcing "cold")

To measure a genuine cold read, we first have to kick the data out of RAM — otherwise the OS would quietly serve it from the page cache and the "cold" number would be fake. We do this with a memory-pressure tool, mem_hog.c: it allocates a big chunk of anonymous memory and touches every 4 KiB page, which forces the kernel to evict the file-backed pages to make room. A bounded loop watches Cached: in /proc/meminfo and keeps hogging until it drops below a threshold.

evict_all() {  # scale-ladder, per node, before each rep
  srun --overlap -N $N -n $N --ntasks-per-node=1 --cpus-per-task=16 bash -c '
    for pass in 1 2 3 4 5; do
      cached_gb=$(awk "/^Cached:/{printf \"%d\", \$2/1048576}" /proc/meminfo)
      [ $cached_gb -le 8 ] && break        # target: Cached <= 8 GB
      hog=$((cached_gb+30)); per=$(( (hog+7)/8 ))
      for i in 1 2 3 4 5 6 7 8; do "$RESULTS_DIR/mem_hog" $per 1 >/dev/null 2>&1 & done; wait
    done'
}

megatron_scale_ladder/…/job.sh:43-59 · gnn_regime_pinned/…/job.sh:44-64 · benchmarks/util/mem_hog.c:64 · (older scripts also use posix_fadvise(POSIX_FADV_DONTNEED): frontier_llm_dataloader_compare.sh:107-120)

Eviction is best-effort, and we say so. On a 512 GiB node with a small working set (the GNN gather touches only ~2.67 GB), mem_hog sometimes cannot flush everything. So for GNN we treat rep 1 (the cleanest eviction) as the anchor result and keep reps 2–3 (which kept some data in RAM) only to show run-to-run spread. Anyone reproducing this should check /proc/meminfo to confirm how cold the run really was.

3.5 The checksum-equality gate (correctness)

This is how we prove the speedup is honest. Every benchmark adds up the bytes it reads into a GLOBAL_CHECKSUM, one per rank. The harness then compares the full set of per-rank checksums (not just rank 0) between FitCachePP and the native baseline. If they are not identical, the result is a FAIL.

pairs() { grep 'SUMMARY' "$1" | sed -nE 's/.*rank=([0-9]+).*GLOBAL_CHECKSUM=([0-9]+).*/\1=\2/p' | sort -n; }
if [ "$(pairs native.log)" = "$(pairs fitcachepp.log)" ]; then echo "CHECKSUM_GATE: PASS"; else echo FAIL; fi

frontier_gnn_warmhit_sweep.sh:159-173 · frontier_megatron_warmhit_sweep.sh:127-132

The exact byte-touch differs a little by workload, but each reduces to a 64-bit integer so it cannot overflow on TB-scale runs: Megatron sums a uint16 view; GNN sums a uint32 view masked to 63 bits; DINOv2 sums a uint8 view masked to 63 bits. Both sides use the same view, so a match is exact. llm_coverage_bench.py:100 · gnn_feature_bench.py:198 · cc12m_mmap_bench.py:170

3.6 Two-view reporting (mechanism vs. amortized)

We always report the speed two ways, so the one-time staging cost is visible:

  • View 1 — the mechanism alone: warm epoch vs. native epoch. This isolates the benefit of reading from the local tier instead of Lustre, ignoring setup cost.
  • View 2 — the honest total: include the one-time pre-stage copy and ask after how many epochs E FitCachePP wins overall, i.e. when pre_stage + E·warm < E·cold. We report this break-even at E = 1…5.

frontier_dinov2_warmhit_sweep.sh:135-147

4. Workload 1 — Megatron (dense-sequential LLM)

An LLM-training data loader. It reads large token files end to end, in order — the easy case for Lustre, so the expected speedup is modest.

Background, from scratch. Megatron-LM is NVIDIA's framework for training large language models (LLMs, the technology behind ChatGPT-style systems) across many GPUs. To train an LLM you feed it a huge amount of text that has already been tokenized — converted from words into a long stream of integer IDs (see §2.1). Megatron stores that stream on disk in a fixed format called an IndexedDataset: a .bin file holding all the integer tokens back-to-back, plus a small .idx file that records where each document starts so the loader can jump to any document. This experiment reproduces exactly that on-disk layout and the way it is read, because reading it is what we want to speed up. We do not care what the text says — only how the bytes are laid out and accessed — so we fill the file with random tokens (see "What" below).

Dataset & format

WhatA synthetic Megatron IndexedDataset — the real on-disk format, but with random (meaningless) contents. The point is to reproduce the exact numpy.memmap read pattern of a tokenized corpus, not to train anything.
Formatshard_NNNN.bin = raw uint16 tokens (2 bytes each); shard_NNNN.idx = the Megatron index written by _IndexWriter(idx, np.uint16). Tokens are uniform-random in [0, 50256); doc length 2048 tokens.
Size16 GiB per shard. Runs use 40 shards (640 GiB/node, for the warm-hit sweep + scale ladder) or 64 shards (a 1 TB corpus). One 16 GiB shard ≈ 4.2 M docs.
Generationpython generate_synth_corpus_sharded.py --output-dir P --num-shards N --shard-bytes $((16*1024**3)) --doc-len 2048 [--seed 42] [--parallel-workers W] (chunked rng.integers(0,50256,dtype=uint16) writes + matching .idx).

What stands in for the "model"

Why "no model"? A real Megatron run does three things per step: (1) read tokens from disk, (2) run them through the neural network on the GPU (the expensive forward/backward pass), (3) update the model's weights. We only want to measure step (1), the reading — step (2) is heavy GPU compute that overlaps with I/O and would make the read time impossible to isolate. So instead of a real model we run a small benchmark, llm_coverage_bench.py, that does only the reading: it reproduces exactly how a real loader would touch the file, but skips the neural network entirely. "The driver is llm_coverage_bench.py" just means this script — not a real LLM — is what drives the experiment.

What it does: it mmaps each shard (see §2.1) and reads a --coverage fraction of it, spread evenly across the shard in --n-chunks contiguous pieces, adding the bytes into GLOBAL_CHECKSUM (the sum both forces the read to really happen and serves as the correctness check). On multiple nodes the shards are split round-robin (rank R of N reads shards [R, R+N, R+2N, …]) so every node does equal work. (A second driver, llm_dataloader_bench_sharded.py, instead reads random sequences via IndexedDataset.get(doc, length=seq_length); the warm-hit sweep uses the coverage bench.)

5. Workload 2 — GNN feature gather (sparse-random, IGB-large)

A graph-learning data loader. It reads a few thousand tiny, scattered feature rows from a huge file — the worst case for Lustre, so this is where FitCachePP wins biggest.

Background, from scratch. A Graph Neural Network (GNN) learns from data shaped like a graph — things ("nodes") connected by relationships ("edges"). Here the graph is IGB-large, an academic citation graph: the nodes are 100 M papers and 117 M authors, and the edges are "paper cites paper" and "paper written by author." Each node carries a feature vector — a row of 1024 numbers describing it. To train, the loader repeatedly: picks some random papers, follows their edges a couple of hops to collect a neighbourhood, and then gathers the feature rows of all those neighbours. The catch: those rows are scattered all over a ~900 GB file and each is only 4 KB, so the access pattern is many tiny reads at random offsets — exactly what a network filesystem like Lustre is worst at. That mismatch is why caching to local storage helps so much here.

Dataset & format

WhatThe real IGB-large academic graph: 100 M paper nodes, 116.96 M author nodes, 2 relations (paper_cites_paper, paper_written_by_author).
FormatNode features are raw float32 numpy arrays — paper_node_feat.npy shape (100 M, 1024) and author_node_feat.npy shape (116.96 M, 1024). Each row is 1024×4 = 4096 B, exactly one page. The graph itself is stored as CSR (int64 indptr + indices).
Sizepaper features 409.6 GB + author features 479.1 GB + CSR (~14 GB) = ~902 GB total (features alone ~889 GB).
GenerationThe CSR is built by build_igb_csr.py from edge_index.npy (argsort by source, bincount for degree, cumsum → indptr). The features are the real IGB-large arrays.

What stands in for the "model"

The "model" is a 2-hop graph sampler that drives a sparse feature gather — there are no GNN layers and no training, just the data access a real sampler would generate:

  1. Pick 1024 random seed papers (hop 0).
  2. Hop 1: sample up to 12 paper→paper neighbours and up to 8 paper→author neighbours (--fanout-pp 12 --fanout-pa 8).
  3. Hop 2: sample up to 8 more paper→paper neighbours of the hop-1 papers (capped at 4096) (--fanout-pp2 8).
  4. Collect the unique paper + author rows touched, then gather them block by block: split the rows into 12 GiB blocks (3,145,728 rows), mmap each block by offset, pull its rows, and sum the uint32 view into the masked checksum.

This touches only ~2.67 GB (~0.3%) of the 902 GB corpus — exactly the small, random, scattered reads that crawl on Lustre. Each epoch is 20 batches × 1024 seed papers.

  • FitCachePP arm: 2 epochs × 3 reps, with a mem_hog eviction before each rep. Epoch 0 = the evicted, NVMe-bound warm hit; epoch 1 = the same data reused from RAM.

The two sides are not symmetric — on purpose, and stated openly. We compare "FitCachePP reading its local copy (warm-hit-prestaged)" against "the native app reading cold from Lustre (separately evicted)." That is not a warm-vs-warm race; it is the actual question we care about — local fast tier vs. the shared filesystem. The checksum gate proves both sides read identical bytes, so the comparison is fair even though the starting conditions differ.

6. Workload 3 — DINOv2 / CC12M (sequential vision tar)

A vision data loader. It streams large image tar files in order — like Megatron, a sequential pattern, so a moderate speedup is expected.

Background, from scratch. DINOv2 is a Meta method for training vision models on images. Its training images are packaged the way large image datasets usually are: bundled into big .tar archive files (here the CC12M dataset — ~12 M web image+caption pairs), with many images per .tar. This "many images in one big sequential file" format is called WebDataset. The loader reads each archive start-to-end and pulls out the images. So the access pattern is large, sequential reads of ~540 MB files — the same easy-for-Lustre shape as Megatron, which is why the expected speedup is moderate rather than huge. This workload is the third access pattern in our set: sequential vision, alongside Megatron (sequential text) and GNN (random gather).

What stands in for the "model"

The unit of work is a "shard pass," not a full-corpus epoch. Each rank mmaps its set of shards and forces every byte through the page-fault path with a vectorized np.sum(dtype=uint64) over the whole shard. Two layouts: disjoint (rank r reads shards [r·num_shards, (r+1)·num_shards)) or shared (--shared: every rank reads [0, num_shards)). As a side correctness check, 1 image in 50 is actually JPEG-decoded with PIL off the timed path (a decode_ok count, e.g. 10956/10956).

7. Method variant — access-aware placement

This variant tests where a cached copy is placed. A warm hit only works if the copy is on the node that needs it; the default hash placement scatters copies across the whole cluster, which breaks that. Two knobs control the experiment:

  • FITCACHE_MMAP_PLACEMENT = hash (default; modulo_select, scattered cluster-wide) or node_local (send the copy to a server on the requesting node).
  • DINO_SHARD_MODE = shared (--shared) or partitioned (drop --shared → disjoint ranges) — this drives the duplication-factor comparison (how many copies of the dataset exist cluster-wide).

The node-local routing math (assuming servers divide evenly across nodes):

// src/cross_job/fitcache_cross_job.cpp:121-158
int spn  = server_count / nnodes;          // servers per node; -1 (→ hash fallback) if not divisible
uint64_t h = fitcache_fnv1a64(path);
int slot = nodeid*spn + (h % spn);         // a server on THIS node (SLURM_NODEID)

What we ran (each cell measured by a resolver probe that counts cache-hit vs. fallback vs. remote, plus the checksum gate): Megatron N=2 & N=4, GNN N=2, DINOv2 N=2 shared, DINOv2 N=2 partitioned (498 shards/node: node 0 reads [0,498), node 1 [498,996)), plus a hash baseline (Megatron N=2) to show the scatter.

8. Method variant — Megatron scale ladder (32–256 nodes)

This variant asks one question: does the warm-hit benefit hold as the job grows? We run the same Megatron workload at 32, 64, 128, and 256 nodes and watch whether the warm epoch time stays flat (it should, if the client-side resolver adds no coordination cost).

  • Regime: 640 GiB/node (40 shards replicated), regime-pinned > 512 GiB RAM; FITCACHE_MMAP_PLACEMENT=node_local.

10. Method variant — sidecar recovery (4 phases)

This variant tests whether the cache survives a server restart. Each cached file gets a small .meta "sidecar" file recording what it is; when a server restarts, it reads those sidecars to rebuild its memory of what is already cached, so the next run warm-hits instead of re-fetching from Lustre. Driven by frontier_sidecar_recovery.sh for any of the three workloads (BENCH=megatron|gnn|dinov2), in four phases:

  1. P1 Populate: bring up server #1 and run a cold epoch — reading a file triggers a promotion that copies it to the local tier and writes its .meta sidecar.
  2. P2 Kill: kill server #1 and wipe the port-cfg file (simulating a crash/restart).
  3. P3 Restart: bring up server #2; restore_from_sidecars scans the tier directories and rebuilds the cache map. The harness waits (≤120 s) until the server log reports total restored = N.
  4. P4 Post-restart pass: re-run the benchmark over the same paths; a probe confirms every file warm-hits (hit==expected, fallback==0), and the checksum must match the populate phase (both run --epochs 2 so the raw checksums are comparable).

A SKIP_POST=1 variant measures restore time only (the restore-scaling sweep over 32 / 256 / 996 objects).

11. Methodological honesty & known limitations

Stated plainly, so the method is reproducible and nobody over-reads the numbers:

  • The two sides start from different states — on purpose. FitCachePP's timed epoch is a warm read of a local copy; the native baseline is a cold read from Lustre (separately evicted). That is the question we are asking — local tier vs. shared filesystem — and the checksum gate proves identical bytes. It is not a warm-vs-warm comparison, and we never present it as one.
  • Eviction is best-effort. On a 512 GiB node with a small working set (GNN ~2.67 GB), mem_hog cannot fully flush RAM, so the GNN headline uses rep 1 (cleanest eviction) as the anchor and keeps reps 2–3 only as variance context.
  • Native Lustre speed depends on cluster conditions. The same native epoch varies with time-of-day contention (e.g. 944–2567 s at fixed N in the scale ladder). The warm side is the stable quantity; any reported speedup inherits the native variance — which is why the GNN result is given per regime (vs. favorable and vs. cold Lustre) instead of a single number.
  • The staging check is size-only, not a content hash (§3.3) — integrity ultimately rests on the end-to-end checksum gate.
  • Working sets are bigger than node RAM on purpose (regime-pinned), so the native baseline cannot hide reads in the page cache; a sub-RAM layout would let both sides cache in RAM and wash the difference out.
  • These are data-loading I/O benchmarks. The "model" is a fixed access pattern plus a byte-touch, not a real forward/backward pass. All claims are scoped to mmap-backed data loading, not end-to-end training.
  • The one-time staging cost is reported separately and only folded back into the amortized (View 2) break-even — it is never hidden inside a warm epoch.
