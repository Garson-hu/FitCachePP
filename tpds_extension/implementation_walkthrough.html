1. The goal — what we want to do

The IPDPS-era FitCache intercepted open / read / pread / close and served cached data over Mercury RPC. The TPDS extension has two new contributions plus one supporting mechanism:

#What we wantWhy it was neededStatus
1Transparent mmap cache path. Make mmap()-based loaders (numpy.memmap → Megatron IndexedDataset, DINOv2 tar slices, GNN feature gather) benefit from the node-local cache, with the warm read served by a direct mmap of the cached file from whichever local tier holds it (DRAM/tmpfs → PMem → NVMe; no RPC).Page-fault reads on an mmap never call read(), so the old client missed them entirely — those workloads measured "0 Open RPC". The data flowed straight from the PFS.DONE
2Prefetch-informed migration + limited replication. The application declares the files it is about to mmap via a new API, fitcache_prefetch(path, replication_mode). The file's owning server migrates the single cached copy (a whole-file peer→local network transfer) onto that node ahead of the read, overlapped with the current epoch's compute. The cluster stores each file once (1×) instead of N×, while every read is still a warm local mmap.A warm mmap hit needs the file in a local cache tier on the same node. The old "cache everything everywhere" default replicated each node's whole working set on every node — N× the dataset. Frontier has no NVMe-oF / remote DAX, so a node cannot mmap a peer's NVMe directly; the copy must physically arrive locally. Doing that lazily at mmap time is no faster than the per-read RPC fallback, so the migration must be prefetched and overlapped with compute.DONE
3.meta file cache-state recovery (supporting). Persist a .meta file per cached file so a restarted metadata service can rebuild its cache map.Lets the cache survive a server restart without re-promoting from PFS. It restores server-side state; it is not the bandwidth source.Supporting

These are not three separable features — they are one system. Mechanism 1 only delivers the warm-hit speedup if the cached copy is node-local; under 1× storage the copy gets there because Mechanism 2 prefetches and migrates it peer→local ahead of the mmap, hidden under the current epoch's compute. And that node-local cache only survives a job requeue or service crash if the server can rebuild its state (Mechanism 3). The key constraint that ties them together: on Frontier a node cannot map a peer's NVMe, so a warm local mmap demands a local copy — and the only way to keep storage at 1× (not N×) while still serving warm local mmaps is to move that single copy in advance, which is precisely what the prefetch interface enables. This walkthrough then explains each mechanism's code in turn. See experiments.html.

3. Mechanism 1 — Transparent mmap cache path DONE

3a. The mmap wrapper

This is the centerpiece, at wrappers.c:490. It interposes on the libc mmap symbol. The logic is: bypass anything we can't safely redirect, then try a warm hit (direct mmap of the cached file), then fall back to a native PFS mmap on a cold miss.

src/client/wrappers.c:490 — entry + safety bypasses 
void* WRAP_DECL(mmap)(void *addr, size_t length, int prot, int flags,
                      int fd, off_t offset)
{
    MAP_OR_FAIL(mmap);                 // resolve __real_mmap via dlsym(RTLD_NEXT)
    MAP_OR_FAIL(munmap);

    if (g_disable_redirect || tl_disable_redirect)
        return __real_mmap(addr, length, prot, flags, fd, offset);   // global/thread kill-switch

    if (fd < 0 || length == 0 ||
        (flags & MAP_ANONYMOUS) || (flags & MAP_FIXED) ||
        ((flags & MAP_SHARED) && (prot & PROT_WRITE)))
        return __real_mmap(addr, length, prot, flags, fd, offset);   // can't safely intercept

Line by line:

  • MAP_OR_FAIL(mmap) / MAP_OR_FAIL(munmap) — resolve the real glibc symbols once (we need munmap too because the tracker undoes the mapping later).
  • The kill-switch check lets internal FitCache code map files without recursing into our own redirect.
  • The big bypass if excludes the cases where redirecting would be wrong: fd<0 / length==0 (nothing to back), MAP_ANONYMOUS (no file), MAP_FIXED (caller demands a specific address), and writable MAP_SHARED (the app expects writes to flush to the file — our redirect can't honor that). Crucially, read-only MAP_SHARED is not bypassed: that is exactly the path numpy.memmap(mode='r') takes (CPython maps ACCESS_READ → MAP_SHARED | PROT_READ), and with no PROT_WRITE there is no write-back to honor, so redirecting it is safe.
src/client/wrappers.c:508 — is this fd one we track? 
    const char *path = fitcache_get_path(fd);
    if (!path)
        return __real_mmap(addr, length, prot, flags, fd, offset);   // untracked fd → passthrough

fitcache_get_path(fd) returns the original PFS path if this fd came through our open wrapper; otherwise we pass through. From here on we know the original path.

src/client/wrappers.c:532 — the warm-hit path (direct local-tier mmap, no RPC) 
    char cached_path[4096];
    double __t0 = fitpp_now_us();
    int __resolved = fitcache_resolve_cached_path(path, cached_path, sizeof(cached_path));
    fitcache_stat_add("mmap.resolve_us", fitpp_now_us() - __t0);
    if (__resolved) {
        int cfd = __real_open(cached_path, O_RDONLY);
        if (cfd >= 0) {
            int map_flags = (flags & MAP_SHARED) ? MAP_SHARED : MAP_PRIVATE;
            void *m = __real_mmap(NULL, length, prot, map_flags, cfd, offset);
            __real_close(cfd);                 // inode stays alive via the mapping
            if (m != MAP_FAILED) {
                fitcache_stat_add("mmap.warmhit_total_us", fitpp_now_us() - __t0);
                fitcache_mmap_tracker_record(m, length);
                return m;                       // ← app now page-faults from the local cache tier
            }
        }
    }

This is the heart of the 2026-05-21 redesign. Step by step:

  1. resolve — fitcache_resolve_cached_path() (next section) deterministically computes where the cached copy would be and confirms it is present + complete. Purely client-side, no Mercury RPC. The two fitcache_stat_add calls time this for the shutdown profile.
  2. open — on a hit, __real_open the cached file on its local tier read-only (the resolver returns whichever of DRAM/PMem/NVMe matched).
  3. map — __real_mmap(NULL, ...) on the cached fd. We honor the caller's prot and sharing flag (read-only, so MAP_SHARED has no write-back concern). The kernel will now satisfy page faults from the local cache tier instead of Lustre.
  4. close — __real_close(cfd) immediately. The mapping keeps the inode alive after the fd is closed (POSIX unlink/close-while-mapped semantics), which also protects an in-use mapping if the eviction reaper unlinks the cached file underneath us.
  5. track + return — record (addr → length) so munmap can undo it, then return the mapping. The app never knows it is reading from a local cache tier instead of the PFS.
Why this beats the old design. The first attempt populated an anonymous region via Mercury bulk transfer at mmap time. That single-stream Mercury bulk path (~900 MB/s) was slower than Lustre itself (~2 GB/s) and far slower than a local cache tier (DRAM/NVMe). The redesign drops Mercury from the read path entirely: the warm hit is just open + mmap of a local file.
src/client/wrappers.c:564 — cold miss 
    /* Cold miss: native mmap on the original PFS file. The file is already
     * tracked via the open RPC, so the server data mover promotes it; the
     * NEXT mmap of this path becomes a warm hit. Cold is never slower than
     * the native baseline. */
    return __real_mmap(addr, length, prot, flags, fd, offset);

On a miss we do exactly what the application would have done without FitCache — a native PFS mmap — so we can never be slower than baseline on the cold pass. Because the open RPC for this fd already fired, the server has enqueued the file for promotion (section 3d), so the next mmap of this path resolves to a warm hit. If a peer already holds the file, that promotion becomes a peer→local migration (Mechanism 2) instead of a fresh PFS copy.

src/client/wrappers.c:584 — mmap64 alias 
void* WRAP_DECL(mmap64)(void *addr, size_t length, int prot, int flags,
                        int fd, off64_t offset)
{
    return WRAP_DECL(mmap)(addr, length, prot, flags, fd, (off_t)offset);
}

This alias matters in practice: CPython's _mmap.so calls mmap64 (the explicit 64-bit variant), not plain mmap. Without intercepting mmap64 the entire numpy.memmap path would skip our redirect. On 64-bit Linux the two are identical, so we just delegate.

3b. The resolver — fitcache_resolve_cached_path()

At fitcache_multi_source_read.cpp:291. This is what makes the warm hit RPC-free: it reconstructs the cached path with the same hashing the server uses, then confirms completeness by size.

src/client/fitcache_multi_source_read.cpp:291 
extern "C" int fitcache_resolve_cached_path(const char *original_path,
                                            char *out, size_t outsz)
{
    if (!original_path || !out || outsz == 0) return 0;

    struct stat ost;
    if (stat(original_path, &ost) != 0 || ost.st_size <= 0) return 0;
    const off_t orig_size = ost.st_size;          // completeness reference

    size_t h = std::hash<std::string>{}(std::string(original_path));
    char subdir[16];
    snprintf(subdir, sizeof(subdir), "%02zx/%02zx", (h >> 8) & 0xFF, h & 0xFF);

    std::string op(original_path);
    size_t slash = op.find_last_of('/');
    std::string base = (slash == std::string::npos) ? op : op.substr(slash + 1);

    const char *tier_env[3] = {
        getenv("FitCache_DRAM_PATH"),
        getenv("FitCache_PMEM_PATH"),
        getenv("FitCache_NVME_PATH"),
    };
    for (int i = 0; i < 3; ++i) {
        const char *t = tier_env[i];
        if (!t || !t[0]) continue;
        std::string cand = std::string(t) + "/" + subdir + "/" + base;
        struct stat cst;
        if (stat(cand.c_str(), &cst) == 0 && S_ISREG(cst.st_mode) &&
            cst.st_size == orig_size) {            // ← the completeness GATE
            std::strncpy(out, cand.c_str(), outsz - 1);
            out[outsz - 1] = '\0';
            return 1;                              // warm hit
        }
    }
    return 0;                                      // miss
}

The key design points:

  • Same hash as the server. std::hash<std::string> of the original path, then a two-level bucket <(h>>8)&0xFF>/<h&0xFF>. The server's data mover and the migration primitive compute the identical bucket (data_mover.cpp:482-484 and data_mover.cpp:86-88). Client and server link the same libstdc++, so the hash value matches bit for bit — this is what lets the client reconstruct the path with no RPC.
  • The completeness gate is cst.st_size == orig_size. The data mover does a full fs::copy (and the migration primitive a full chunked pull) before a file is usable; if a partial copy is on disk its size won't match, and we correctly treat it as a miss and fall through to the PFS. This is what makes the warm hit safe to take without asking the server — and it is exactly why a migration must complete before its rename publishes the file (section 4c).
  • Tier-general, DRAM-first. The probe order is tier_env[3] = {DRAM_PATH, PMEM_PATH, NVME_PATH} and the warm hit maps whichever tier matched — the returned cand path is tier-agnostic. This mirrors the server data mover, which places a promoted file DRAM (tmpfs) first, then PMem, then NVMe by remaining capacity (data_mover.cpp:443-466: target_tier = CACHE_TIER_DRAM unless DRAM is full). So the mechanism is a tiered node-local cache, not an NVMe-only cache.
  • Server-map independent. Notice it only stat()s the filesystem; it never consults a server. This is why the with/no-.meta file ablation (section 5) shows the client warm-hits in both arms — the resolver needs only the files on disk, not the server's in-memory map.
Mechanism vs. what the Frontier experiments used — and why not tmpfs. The cache is tier-general (DRAM/tmpfs → PMem → NVMe, DRAM-first by capacity), but the reported warm-hit numbers were served from NVMe, not DRAM. What decides tmpfs feasibility is the per-node working set, which depends on the access pattern, not on the total dataset size. The un-partitionable GNN workload keeps the per-node set larger than the 512 GiB node RAM: its sparse 2-hop gather can touch any feature row, so each node must hold the whole feat+CSR set (~902 GB) and the resolver requires a complete file — NVMe (/mnt/bb burst buffer, ~2 TB/node) is the only local tier large enough. (The warm hit lands on NVMe because that is where the migrated/promoted copy was written; the client resolver does no RPC and never reads FitCache_DRAM_CAPACITY — a server-only knob.)

The partitionable case. Under a partitionable access pattern — Megatron dense-sequential and DINOv2 sequential vision — each node touches only its own 1/N partition. With prefetch-informed migration the cluster stores each file once (1×) and each node's resident set is just its partition, e.g. at 16 nodes a DINOv2 node holds ~62 shards ≈ 34 GB/node, which does fit a per-node tmpfs. So tmpfs caching is feasible there. The catch is that once the per-node set fits in RAM, the Native_mmap_PFS baseline page-caches it too (an mmap of a tmpfs file and a page-cached Lustre file fault from the same kind of RAM pages), so the warm→warm gap collapses toward parity — the real benefit is the cold→warm gap (native first cold read vs. FitCachePP warm). Net: NVMe is the correct tier for the un-partitionable GNN's >RAM working set; for the partitionable workloads the headline is 1× cluster storage with warm local mmaps, with the benefit measured cold→warm. Defer all numbers to experiments.html.

3c. The mmap tracker + munmap

Because we returned a mapping of the cached file (a different length bookkeeping than the caller may assume), munmap needs to know the exact length we mapped. The tracker is a tiny mutex-guarded map at fitcache_mmap_tracker.cpp:

src/client/fitcache_mmap_tracker.cpp 
std::unordered_map<void*, size_t> g_addr_to_length;   // guarded by g_mtx

void   fitcache_mmap_tracker_record(void *addr, size_t length);  // insert on warm hit
size_t fitcache_mmap_tracker_lookup(void *addr);                 // 0 if not ours
void   fitcache_mmap_tracker_drop(void *addr);                   // erase on munmap

mmap is not a hot path (one call per file open in a training job), so a single global mutex is fine. The munmap wrapper at wrappers.c:590 uses it:

src/client/wrappers.c:590 
int WRAP_DECL(munmap)(void *addr, size_t length)
{
    MAP_OR_FAIL(munmap);
    size_t tracked_len = fitcache_mmap_tracker_lookup(addr);
    if (tracked_len > 0) {
        fitcache_mmap_tracker_drop(addr);
        return __real_munmap(addr, tracked_len);    // use OUR length, not the caller's
    }
    return __real_munmap(addr, length);             // not ours → caller's length
}

If the address is one we handed out, we unmap with the length we recorded (numpy.memmap sometimes rounds the user-visible length, so the tracker value is authoritative). Otherwise we defer to the caller's length.

3d. Open-time promotion (filling the cache)

The warm-hit path is only useful if the cache actually gets populated. That happens on the server when an open RPC arrives, at fitcache_comm_server.cpp:400:

src/comm/fitcache_comm_server.cpp:400 
        bool need_promote = false;
        {
            std::unique_lock<std::shared_mutex> wlock(cache_mtx);
            fd_to_path[out.ret_status] = path_str;
            need_promote = (path_cache_map.find(path_str) == path_cache_map.end());
        }
        // Promote at OPEN time (not only at close)...
        if (need_promote) {
            L4C_INFO("Open-time promote enqueue: %s", path_str.c_str());
            pthread_mutex_lock(&data_mutex);
            data_queue.push(path_str);
            pthread_cond_signal(&data_cond);
            pthread_mutex_unlock(&data_mutex);

Why open-time, not close-time. numpy.memmap reuses the same fd per shard. Under that access pattern the client's open_cb response is sometimes dropped as stale by the epoch guard, leaving fd_redir_map[fd]==0, which makes the client skip the close RPC — so close-time promotion never fired and the cache stayed empty (exactly the cache the warm-hit path needs). Enqueuing at open time guarantees promotion regardless of the close RPC. The data mover dedups against path_cache_map, so a double enqueue is harmless. The prefetch hint (section 4) uses this same enqueue, just proactively and ahead of the open.

The data mover thread then does the physical copy (or, when a peer already holds the file, a peer→local migration) and computes the cached path — covered in section 4c and in section 3 of Mechanism 3 below, because the same landing code also writes the .meta file.

4. Mechanism 2 — Prefetch-informed migration + limited replication DONE

A warm mmap hit needs the cached file on the requester's own node, but Frontier has no NVMe-oF / remote DAX — a node cannot mmap a peer's NVMe across the fabric. So the single cached copy must physically arrive on the local tier before the read. The old default solved that by replicating each node's whole working set on every node (N× the dataset). The TPDS extension instead keeps one copy cluster-wide and migrates it peer→local just-in-time. The catch: doing the migration lazily at mmap time is no faster than the existing per-read RPC fallback — the transfer is on the critical path. It only pays off when it is prefetched and overlapped with the current epoch's compute. That is why the prefetch interface is load-bearing.

4a. fitcache_prefetch() — the prefetch C API

The application declares the files it is about to mmap (e.g. next epoch's shards) by calling fitcache_prefetch(), a new extern "C" symbol exported from the LD_PRELOAD client. It is declared in fitcache_multi_source_read.h:35 and implemented at fitcache_multi_source_read.cpp:34:

src/client/fitcache_multi_source_read.h:32 + .cpp:34 
// header (fitcache_multi_source_read.h:32)
// owning server, which promotes the file ahead of the read. replication_mode
// follows fitcache_replication_mode_t (0 = unbounded = today's behavior).
int fitcache_prefetch(const char *original_path, int replication_mode);

// impl (fitcache_multi_source_read.cpp:34)
extern "C" int fitcache_prefetch(const char *original_path, int replication_mode)
{
    if (!original_path || !original_path[0]) return -1;
    if (g_fitcache_server_count == 0) return -1;
    fitcache_client_ensure_comm_init();          // prefetch may run before any open
    std::string path(original_path);
    int slot = fitcache::select_server_for_path(path,
                                static_cast<int>(g_fitcache_server_count));
    if (slot < 0) return -1;                      // can't route → no-op
    fitcache_client_comm_gen_prefetch_rpc(static_cast<uint32_t>(slot), path,
                                          replication_mode, 0);
    return 0;                                     // fire-and-forget
}

Line by line:

  • Routing reuses the read path. select_server_for_path() resolves the file's owning server slot exactly the way ms_read routes a read, so the hint lands on the server that already owns (or will own) this path — no new routing policy is introduced.
  • Lazy comm init. The open interceptor brings Mercury up on the first open, but a prefetch can run before any open (that is the point — declare next epoch's files while this epoch computes), so it calls fitcache_client_ensure_comm_init() first.
  • Fire-and-forget. It forwards a non-blocking RPC and returns immediately; the app never waits on the transfer. The migration runs on the server, overlapped with the app's compute. The replication_mode argument is passed straight through (the 0 is the replication cap, defaulted here).
  • Graceful when absent. Reachable via LD_PRELOAD through wrappers.c like every other interposed symbol; on a Native_mmap_PFS baseline run with no preload the symbol simply isn't there and the benchmark shim treats every call as a no-op (section 4d).

The client forwards it fire-and-forget at fitcache_comm_client.cpp:682 (fitcache_client_comm_gen_prefetch_rpc), whose completion callback only logs the ack and tears down the handle — the app does not block on it. The server side handles it at fitcache_comm_server.cpp:922:

src/comm/fitcache_comm_server.cpp:922 — fitcache_prefetch_rpc_handler 
hg_return_t
fitcache_prefetch_rpc_handler(hg_handle_t handle)
{
    fitcache_prefetch_in_t in;
    HG_Get_input(handle, &in);
    std::string path_str = (in.path && in.path[0]) ? in.path : std::string();
    int mode = in.replication_mode;              // forwarded to the policy
    HG_Free_input(handle, &in);

    fitcache_prefetch_out_t out;  out.tier = 0;
    bool local_hit = false;
    if (!path_str.empty()) {
        std::shared_lock<std::shared_mutex> rlock(cache_mtx);
        local_hit = (path_cache_map.find(path_str) != path_cache_map.end());
    }

    if (path_str.empty()) {
        out.status = FITCACHE_PREFETCH_ERR;
    } else if (local_hit) {
        out.status = FITCACHE_PREFETCH_HIT;       // already on this node → nothing to do
    } else {
        L4C_INFO("Prefetch enqueue: %s (replication_mode=%d)", path_str.c_str(), mode);
        pthread_mutex_lock(&data_mutex);
        data_queue.push(path_str);                // SAME queue the open-time promote uses
        pthread_cond_signal(&data_cond);
        pthread_mutex_unlock(&data_mutex);
        out.status = FITCACHE_PREFETCH_QUEUED;
    }

    HG_Respond(handle, NULL, NULL, &out);
    HG_Destroy(handle);
    return HG_SUCCESS;
}

The handler is deliberately thin: if the file is already local it answers HIT and does nothing; otherwise it pushes the path onto the same data_queue the open-time promote uses (section 3d) and answers QUEUED, returning immediately with PREFETCH priority so the transfer runs asynchronously on the data-mover thread and overlaps the app's compute. The actual peer→local move is decided there.

4c. fitcache_server_migrate_file() — the whole-file peer→local transfer

This is the crux primitive. When the data-mover thread drains the queue, it asks: does a peer already cache this file? If so, it pulls the single copy peer→local in one whole-file bulk transfer instead of promoting a fresh copy from the PFS. That decision is at fitcache_data_mover.cpp:581:

The primitive itself is at fitcache_data_mover.cpp:53. It is the part that distinguishes a real migration from the old per-read RPC fallback: it moves the whole file in bulk (chunked only to respect Mercury's ~2 GiB single-RMA cap), not byte ranges per pread:

src/server/fitcache_data_mover.cpp:53 — fitcache_server_migrate_file (abridged) 
int fitcache_server_migrate_file(const std::string &original_path,
                                 const std::string &src_addr, int requested_tier)
{
    { std::shared_lock<std::shared_mutex> rlock(cache_mtx);
      if (path_cache_map.count(original_path)) return 0; }   // already local

    uint64_t file_size = fs::file_size(original_path);        // PFS original = same size
    // pick tier base (NVMe default; DRAM/PMem if requested + set) ...

    size_t h = std::hash<std::string>{}(original_path);       // SAME bucket as the resolver
    snprintf(subdir, sizeof(subdir), "%02zx/%02zx", (h >> 8) & 0xFF, h & 0xFF);
    std::string dst = base + "/" + subdir + "/" + fs::path(original_path).filename().string();
    std::string tmp = dst + ".part." + getpid() + "." + migrate_seq++;   // unique temp

    const size_t CHUNK = (size_t)1 << 30;                     // 1 GiB (single RMA caps ~2 GiB)
    while (done < file_size) {                                // ONE whole-file bulk pull
        int64_t got = fitcache_comm_migrate_pull_chunk(src_addr, original_path,
                                                       done, want, buf, CHUNK);
        if (got <= 0) { rc = -1; break; }
        write(dfd, buf, got);  done += got;
    }
    if (rc != 0 || done != file_size) { unlink(tmp); return -1; }   // incomplete → fail closed
    rename(tmp.c_str(), dst.c_str());                        // publish atomically (completeness gate)

    { std::unique_lock<std::shared_mutex> wlock(cache_mtx);
      path_cache_map[original_path] = dst; }                 // register
    // charge the tier it landed in; bump g_{dram,pmem,nvme}_used_bytes
    if (fitcache::persist_meta_enabled()) {                  // .meta with the replication mode
        auto meta = fitcache::meta_make_initial(original_path, file_size,
                        fitcache::get_self_dataset_manifest_hash(),
                        fitcache::FITCACHE_REPL_SINGLE_COPY, 0);
        fitcache::meta_write_sidecar(dst, meta);
    }
    fitcache_broadcast_register_file(original_path);         // tell peers we now hold it
    return 0;
}

Why each piece matters:

  • Whole-file, not per-read. The loop pulls the entire file in ≤1 GiB chunks via fitcache_comm_migrate_pull_chunk — one bulk transfer of the complete file, contrasted with the per-pread RPC loop that the read fallback uses. Only a complete local copy lets the resolver take a warm mmap (the size-equality gate of section 3b), and only a node-local file is mmappable at all (no remote DAX).
  • Same hash bucket. It writes to the identical two-level bucket the resolver and the PFS promote compute, so the client finds the migrated copy with no message.
  • Atomic publish = the completeness contract. It writes to a per-pid/per-seq .part temp and only renames after done == file_size. A partial pull is never visible, so the resolver never half-hits a migration in flight; an incomplete transfer fails closed and falls back to a PFS promote.
  • Single cluster copy. On success the server registers the file, charges the tier it landed in, writes a .meta with FITCACHE_REPL_SINGLE_COPY, and broadcasts presence — so the cluster holds exactly one copy and peers know where it is. (After a migrate the source copy is evictable; storage stays 1×.)

The same primitive is invoked from two places: the prefetch / open-time enqueue path drains through the migrate-first branch at data_mover.cpp:584, and a standalone server-only smoke path exercises it directly over real Mercury bulk at fitcache_server.cpp:237 (registered alongside the prefetch and migrate-chunk RPCs at fitcache_server.cpp:137-138).

Why lazy migration would not help. If the migration ran at mmap time, the app would block on a single whole-file network transfer before its first page fault — no better than the per-read RPC fallback it replaces, and on Frontier (no remote DAX) there is no way to start mapping before the bytes are local. Prefetch moves that transfer off the critical path: the app declares next epoch's files via fitcache_prefetch() while still computing the current epoch, the server migrates them in the background, and by the time the read arrives it is a warm local mmap. The interface is therefore not a convenience — it is what makes 1× storage compatible with warm local mmaps.

4d. replication_mode/cap — 1× vs limited vs replicate-all

The replication policy is a small enum threaded end to end: the API argument → the RPC fields (replication_mode, replication_cap in fitcache_prefetch_in_t) → the client forward at fitcache_comm_client.cpp:682 → the handler → the .meta record. The modes are defined in fitcache_persistent_meta.h:48:

src/cross_job/fitcache_persistent_meta.h:48 
enum fitcache_replication_mode_t {
    FITCACHE_REPL_UNBOUNDED   = 0,  // old default: replicate-all, no cap (N x)
    FITCACHE_REPL_SINGLE_COPY = 1,  // one copy cluster-wide; migrate peer->local on demand
    FITCACHE_REPL_BOUNDED_K   = 2,  // at most replication_cap copies (hot / concurrent files)
};
// meta v2 (FITCACHE_META_VERSION = 2) adds the two fields:
//   uint32_t replication_mode;     // fitcache_replication_mode_t (0 = unbounded, default)
//   uint32_t replication_cap;      // bounded-k copy cap (0 = unlimited / N/A)
  • SINGLE_COPY=1 — one copy cluster-wide; a node that needs the file but doesn't have it migrates it peer→local (section 4c). This is the 1×-storage mode for partitionable workloads.
  • BOUNDED_K=2 — at most replication_cap copies, for hot / concurrently-read files where a single copy would be a contention point. The cap rides in the RPC and is recorded in the .meta so eviction/placement can honor it.
  • UNBOUNDED=0 — the old replicate-all default; the field defaults to 0 so existing behavior is bit-for-bit unchanged unless a prefetch asks for a stricter mode.

The mode is persisted in the cached file's .meta record at landing time (the meta_make_initial(..., FITCACHE_REPL_SINGLE_COPY, 0) call in fitcache_server_migrate_file above), so the policy survives a restart along with the rest of the cache state (Mechanism 3).

How the benchmarks drive it. The harness calls the API through a ctypes shim, benchmarks/fitcache_prefetch_shim.py, which resolves fitcache_prefetch out of libfitcache_client.so (already resident under LD_PRELOAD) and exposes prefetch(path, mode=REPL_SINGLE_COPY). Each loader calls it just before mmapping an upcoming shard; if the library or symbol is absent (a Native_mmap_PFS baseline with no preload) every call is a no-op returning -1, so the baseline behaves exactly as before. The shim's REPL_* constants are kept in lockstep with the C enum.

5d. The persist_meta_enabled() gate

.meta file write + restore is decoupled from the heavyweight cross-job machinery, at cross_job.cpp:171:

src/cross_job/fitcache_cross_job.cpp:171 
bool persist_meta_enabled() {
    static int cached = -1;
    if (cached < 0) {
        const char *v = std::getenv("FitCache_PERSIST_META");
        int explicit_on = (v && std::strcmp(v, "1") == 0) ? 1 : 0;
        cached = (explicit_on || cross_job_enabled()) ? 1 : 0;   // auto-on under cross-job
    }
    return cached != 0;
}

Why this exists: the original gate ran the full cross-job stack (registry init + heartbeat + sibling-refresh threads) for any test that merely wanted .meta file persistence, and those background threads skewed Horovod ranks at scale. FitCache_PERSIST_META=1 turns on just the .meta file write + restore — no registry, no peer-lookup, no extra threads — so a single-job run can get cache durability across restart without the latency tax. It is auto-on under cross-job (which needs the .meta files for peer discovery, and is the mode in which peer→local migration of Mechanism 2 is active).
