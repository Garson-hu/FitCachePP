1. The goal — what we want to do

The IPDPS-era FitCache intercepted open / read / pread / close and served cached data over Mercury RPC. The TPDS extension has two new contributions plus one supporting mechanism:

#What we wantWhy it was neededStatus
1Transparent mmap cache path. Make mmap()-based loaders (numpy.memmap → Megatron IndexedDataset, DINOv2 tar slices, GNN feature gather) benefit from the node-local cache, with the warm read served by a direct mmap of the cached file from whichever local tier holds it (DRAM/tmpfs → PMem → NVMe; no RPC).Page-fault reads on an mmap never call read(), so the old client missed them entirely — those workloads measured "0 Open RPC". The data flowed straight from the PFS.DONE
2Access-aware mmap cache placement. Make the cached file land on the same node as the rank that needs it, and support disjoint (partitioned) access without full replication.A warm mmap hit needs the file in a local cache tier (DRAM/PMem/NVMe) on the same node. Default hash placement scatters a node's working set across the cluster, so at N≥2 a node misses half its own set.DONE
3.meta file cache-state recovery (supporting). Persist a .meta file per cached file so a restarted metadata service can rebuild its cache map.Lets the cache survive a server restart without re-promoting from PFS. It restores server-side state; it is not the bandwidth source.Supporting

These are not three separable features — they are one system. Mechanism 1 only delivers the warm-hit speedup if the cached copy is node-local (Mechanism 2), and that node-local cache only survives a job requeue or service crash if the server can rebuild its state (Mechanism 3). They are therefore validated together first: a single integrated Megatron N=16 run drives organic promotion → node-local placement (local=160, remote=0) → a live server restart (restore_from_sidecars rebuilds 40/40 in 5 s) → warm hit (fallback=0), with no manual staging and all gates passing. This walkthrough then explains each mechanism's code in turn. See experiments.html §1.1 and experiments_methodology.html §8b.

2. Architecture at a glance

An application links the LD_PRELOAD client (libfitcache_client.so); Mercury-RPC servers run alongside (default 4/node). The path through the system for an mmap-based loader:

app mmap()/mmap64()  ──►  wrappers.c::mmap   (LD_PRELOAD interposition)
                              │
                    ┌─────────┴───────────┐
              WARM HIT                 COLD MISS
                    │                       │
   fitcache_resolve_cached_path()    __real_mmap on the PFS file
   (client-side, deterministic,            │  (open RPC already fired →
    size-match gate, NO RPC)               │   server enqueues promotion)
                    │                       │
   __real_open(cached file, local tier) data mover: select_server_for_path()
   __real_mmap(...) → page-fault           │   picks the slot (Mechanism 2)
   straight from local cache tier    fs::copy(PFS → selected local tier:
                                              DRAM/tmpfs → PMem → NVMe)
                    │                 meta_write_sidecar(...)  (Mechanism 3)
   record (addr→len) in tracker            │
                    │                 NEXT mmap of this path = WARM HIT
   return mapping to app

server restart ──► restore_from_sidecars() rebuilds path_cache_map

3. Mechanism 1 — Transparent mmap cache path DONE

3a. The mmap wrapper

This is the centerpiece, at wrappers.c:490. It interposes on the libc mmap symbol. The logic is: bypass anything we can't safely redirect, then try a warm hit (direct mmap of the cached file), then fall back to a native PFS mmap on a cold miss.

src/client/wrappers.c:490 — entry + safety bypasses 
void* WRAP_DECL(mmap)(void *addr, size_t length, int prot, int flags,
                      int fd, off_t offset)
{
    MAP_OR_FAIL(mmap);                 // resolve __real_mmap via dlsym(RTLD_NEXT)
    MAP_OR_FAIL(munmap);

    if (g_disable_redirect || tl_disable_redirect)
        return __real_mmap(addr, length, prot, flags, fd, offset);   // global/thread kill-switch

    if (fd < 0 || length == 0 ||
        (flags & MAP_ANONYMOUS) || (flags & MAP_FIXED) ||
        ((flags & MAP_SHARED) && (prot & PROT_WRITE)))
        return __real_mmap(addr, length, prot, flags, fd, offset);   // can't safely intercept

Line by line:

  • MAP_OR_FAIL(mmap) / MAP_OR_FAIL(munmap) — resolve the real glibc symbols once (we need munmap too because the tracker undoes the mapping later).
  • The kill-switch check lets internal FitCache code map files without recursing into our own redirect.
  • The big bypass if excludes the cases where redirecting would be wrong: fd<0 / length==0 (nothing to back), MAP_ANONYMOUS (no file), MAP_FIXED (caller demands a specific address), and writable MAP_SHARED (the app expects writes to flush to the file — our redirect can't honor that). Crucially, read-only MAP_SHARED is not bypassed: that is exactly the path numpy.memmap(mode='r') takes (CPython maps ACCESS_READ → MAP_SHARED | PROT_READ), and with no PROT_WRITE there is no write-back to honor, so redirecting it is safe.
src/client/wrappers.c:508 — is this fd one we track? 
    const char *path = fitcache_get_path(fd);
    if (!path)
        return __real_mmap(addr, length, prot, flags, fd, offset);   // untracked fd → passthrough

fitcache_get_path(fd) returns the original PFS path if this fd came through our open wrapper; otherwise we pass through. From here on we know the original path.

src/client/wrappers.c:532 — the warm-hit path (direct local-tier mmap, no RPC) 
    char cached_path[4096];
    double __t0 = fitpp_now_us();
    int __resolved = fitcache_resolve_cached_path(path, cached_path, sizeof(cached_path));
    fitcache_stat_add("mmap.resolve_us", fitpp_now_us() - __t0);
    if (__resolved) {
        int cfd = __real_open(cached_path, O_RDONLY);
        if (cfd >= 0) {
            int map_flags = (flags & MAP_SHARED) ? MAP_SHARED : MAP_PRIVATE;
            void *m = __real_mmap(NULL, length, prot, map_flags, cfd, offset);
            __real_close(cfd);                 // inode stays alive via the mapping
            if (m != MAP_FAILED) {
                fitcache_stat_add("mmap.warmhit_total_us", fitpp_now_us() - __t0);
                fitcache_mmap_tracker_record(m, length);
                return m;                       // ← app now page-faults from the local cache tier
            }
        }
    }

This is the heart of the 2026-05-21 redesign. Step by step:

  1. resolve — fitcache_resolve_cached_path() (next section) deterministically computes where the cached copy would be and confirms it is present + complete. Purely client-side, no Mercury RPC. The two fitcache_stat_add calls time this for the shutdown profile.
  2. open — on a hit, __real_open the cached file on its local tier read-only (the resolver returns whichever of DRAM/PMem/NVMe matched).
  3. map — __real_mmap(NULL, ...) on the cached fd. We honor the caller's prot and sharing flag (read-only, so MAP_SHARED has no write-back concern). The kernel will now satisfy page faults from the local cache tier instead of Lustre.
  4. close — __real_close(cfd) immediately. The mapping keeps the inode alive after the fd is closed (POSIX unlink/close-while-mapped semantics), which also protects an in-use mapping if the eviction reaper unlinks the cached file underneath us.
  5. track + return — record (addr → length) so munmap can undo it, then return the mapping. The app never knows it is reading from a local cache tier instead of the PFS.
Why this beats the old design. The first attempt populated an anonymous region via Mercury bulk transfer at mmap time. That single-stream Mercury bulk path (~900 MB/s) was slower than Lustre itself (~2 GB/s) and far slower than a local cache tier (DRAM/NVMe). The redesign drops Mercury from the read path entirely: the warm hit is just open + mmap of a local file.
src/client/wrappers.c:564 — cold miss 
    /* Cold miss: native mmap on the original PFS file. The file is already
     * tracked via the open RPC, so the server data mover promotes it; the
     * NEXT mmap of this path becomes a warm hit. Cold is never slower than
     * the native baseline. */
    return __real_mmap(addr, length, prot, flags, fd, offset);

On a miss we do exactly what the application would have done without FitCache — a native PFS mmap — so we can never be slower than baseline on the cold pass. Because the open RPC for this fd already fired, the server has enqueued the file for promotion (section 3d), so the next mmap of this path resolves to a warm hit.

src/client/wrappers.c:584 — mmap64 alias 
void* WRAP_DECL(mmap64)(void *addr, size_t length, int prot, int flags,
                        int fd, off64_t offset)
{
    return WRAP_DECL(mmap)(addr, length, prot, flags, fd, (off_t)offset);
}

This alias matters in practice: CPython's _mmap.so calls mmap64 (the explicit 64-bit variant), not plain mmap. Without intercepting mmap64 the entire numpy.memmap path would skip our redirect. On 64-bit Linux the two are identical, so we just delegate.

3b. The resolver — fitcache_resolve_cached_path()

At fitcache_multi_source_read.cpp:291. This is what makes the warm hit RPC-free: it reconstructs the cached path with the same hashing the server uses, then confirms completeness by size.

src/client/fitcache_multi_source_read.cpp:291 
extern "C" int fitcache_resolve_cached_path(const char *original_path,
                                            char *out, size_t outsz)
{
    if (!original_path || !out || outsz == 0) return 0;

    struct stat ost;
    if (stat(original_path, &ost) != 0 || ost.st_size <= 0) return 0;
    const off_t orig_size = ost.st_size;          // completeness reference

    size_t h = std::hash<std::string>{}(std::string(original_path));
    char subdir[16];
    snprintf(subdir, sizeof(subdir), "%02zx/%02zx", (h >> 8) & 0xFF, h & 0xFF);

    std::string op(original_path);
    size_t slash = op.find_last_of('/');
    std::string base = (slash == std::string::npos) ? op : op.substr(slash + 1);

    const char *tier_env[3] = {
        getenv("FitCache_DRAM_PATH"),
        getenv("FitCache_PMEM_PATH"),
        getenv("FitCache_NVME_PATH"),
    };
    for (int i = 0; i < 3; ++i) {
        const char *t = tier_env[i];
        if (!t || !t[0]) continue;
        std::string cand = std::string(t) + "/" + subdir + "/" + base;
        struct stat cst;
        if (stat(cand.c_str(), &cst) == 0 && S_ISREG(cst.st_mode) &&
            cst.st_size == orig_size) {            // ← the completeness GATE
            std::strncpy(out, cand.c_str(), outsz - 1);
            out[outsz - 1] = '\0';
            return 1;                              // warm hit
        }
    }
    return 0;                                      // miss
}

The key design points:

  • Same hash as the server. std::hash<std::string> of the original path, then a two-level bucket <(h>>8)&0xFF>/<h&0xFF>. The server's data mover computes the identical bucket (section 3d, data_mover.cpp:482-484). Client and server link the same libstdc++, so the hash value matches bit for bit — this is what lets the client reconstruct the path with no RPC.
  • The completeness gate is cst.st_size == orig_size. The data mover does a full fs::copy before a file is usable; if a partial copy is on disk its size won't match, and we correctly treat it as a miss and fall through to the PFS. This is what makes the warm hit safe to take without asking the server.
  • Tier-general, DRAM-first. The probe order is tier_env[3] = {DRAM_PATH, PMEM_PATH, NVME_PATH} and the warm hit maps whichever tier matched — the returned cand path is tier-agnostic. This mirrors the server data mover, which places a promoted file DRAM (tmpfs) first, then PMem, then NVMe by remaining capacity (data_mover.cpp:443-466: target_tier = CACHE_TIER_DRAM unless DRAM is full). So the mechanism is a tiered node-local cache, not an NVMe-only cache.
  • Server-map independent. Notice it only stat()s the filesystem; it never consults a server. This is why the with/no-.meta file ablation (section 5) shows the client warm-hits in both arms — the resolver needs only the files on disk, not the server's in-memory map.
Mechanism vs. what the Frontier experiments used — and why not tmpfs. The cache is tier-general (DRAM/tmpfs → PMem → NVMe, DRAM-first by capacity), but the reported warm-hit numbers were served from NVMe, not DRAM. What decides tmpfs feasibility is the per-node working set, which depends on the access pattern, not on the total dataset size. These sweeps keep the per-node set larger than the 512 GiB node RAM on purpose, by replicating it on every node: the Megatron stage loop copies all 40 shards (640 GiB) to every node, the GNN stage loop copies the whole feature files (~902 GB) to every node (it must — the random row-gather can touch any row, and the resolver requires a complete file), and DINOv2 full-corpus runs in shared mode (all 996 shards, 541 GB, per node). Because the per-node set is replicated, aggregating DRAM across N nodes does not shrink it — each node still needs the whole set locally, which a per-node tmpfs (/tmp is tmpfs on Frontier, but RAM-sized) cannot hold. NVMe (/mnt/bb burst buffer, ~2 TB/node) is the only local tier large enough. (The warm hit lands on NVMe because that is where the pre-stage cp wrote it; the client resolver does no RPC and never reads FitCache_DRAM_CAPACITY — a server-only knob, 256 MiB for DINOv2/GNN, 40 GiB for Megatron.)

The partitioned exception (you are right here). Under a partitioned access pattern — DINOv2 disjoint mode, i.e. the Access-Aware partitioned placement of Mechanism 2 — each node caches only 1/N of the corpus, so at 16 nodes ~62 shards ≈ 34 GB/node, which does fit a per-node tmpfs, and the aggregate 16×DRAM holds the whole dataset. So tmpfs caching is feasible there. The catch is that once the per-node set fits in RAM, the Native_mmap_PFS baseline page-caches it too (an mmap of a tmpfs file and a page-cached Lustre file fault from the same kind of RAM pages), so the sustained warm-hit gap collapses toward parity — which is exactly the page-cache artifact the over-RAM sizing was chosen to avoid. Net: NVMe is the correct tier for a sustained warm-hit claim with these (replicated, >RAM) working sets; a DRAM/tmpfs datapoint is feasible under partitioned placement but measures a different (cold-start / under-memory-pressure) gap, not a better-configured version of these sweeps. (Refs: frontier_megatron_warmhit_sweep.sh:6,76-83 replicated stage; frontier_gnn_warmhit_sweep.sh:88-101 whole-file stage; frontier_dinov2_warmhit_sweep.sh:80-88 shared/disjoint base.)

3c. The mmap tracker + munmap

Because we returned a mapping of the cached file (a different length bookkeeping than the caller may assume), munmap needs to know the exact length we mapped. The tracker is a tiny mutex-guarded map at fitcache_mmap_tracker.cpp:

src/client/fitcache_mmap_tracker.cpp 
std::unordered_map<void*, size_t> g_addr_to_length;   // guarded by g_mtx

void   fitcache_mmap_tracker_record(void *addr, size_t length);  // insert on warm hit
size_t fitcache_mmap_tracker_lookup(void *addr);                 // 0 if not ours
void   fitcache_mmap_tracker_drop(void *addr);                   // erase on munmap

mmap is not a hot path (one call per file open in a training job), so a single global mutex is fine. The munmap wrapper at wrappers.c:590 uses it:

src/client/wrappers.c:590 
int WRAP_DECL(munmap)(void *addr, size_t length)
{
    MAP_OR_FAIL(munmap);
    size_t tracked_len = fitcache_mmap_tracker_lookup(addr);
    if (tracked_len > 0) {
        fitcache_mmap_tracker_drop(addr);
        return __real_munmap(addr, tracked_len);    // use OUR length, not the caller's
    }
    return __real_munmap(addr, length);             // not ours → caller's length
}

If the address is one we handed out, we unmap with the length we recorded (numpy.memmap sometimes rounds the user-visible length, so the tracker value is authoritative). Otherwise we defer to the caller's length.

3d. Open-time promotion (filling the cache)

The warm-hit path is only useful if the cache actually gets populated. That happens on the server when an open RPC arrives, at fitcache_comm_server.cpp:400:

src/comm/fitcache_comm_server.cpp:400 
        bool need_promote = false;
        {
            std::unique_lock<std::shared_mutex> wlock(cache_mtx);
            fd_to_path[out.ret_status] = path_str;
            need_promote = (path_cache_map.find(path_str) == path_cache_map.end());
        }
        // Promote at OPEN time (not only at close)...
        if (need_promote) {
            L4C_INFO("Open-time promote enqueue: %s", path_str.c_str());
            pthread_mutex_lock(&data_mutex);
            data_queue.push(path_str);
            pthread_cond_signal(&data_cond);
            pthread_mutex_unlock(&data_mutex);
        }
Why open-time, not close-time. numpy.memmap reuses the same fd per shard. Under that access pattern the client's open_cb response is sometimes dropped as stale by the epoch guard, leaving fd_redir_map[fd]==0, which makes the client skip the close RPC — so close-time promotion never fired and the cache stayed empty (exactly the cache the warm-hit path needs). Enqueuing at open time guarantees promotion regardless of the close RPC. The data mover dedups against path_cache_map, so a double enqueue is harmless.

The data mover thread then does the physical copy and computes the cached path — covered in section 3 of Mechanism 3 below, because the same code also writes the .meta file.

4. Mechanism 2 — Access-aware mmap cache placement DONE

A warm hit needs the cached file on the requester's own node. Placement is decided when the data mover picks which server slot a path's promotion routes to. All of this lives in fitcache_cross_job.cpp.

4b. node_local_select() — the node-local math

src/cross_job/fitcache_cross_job.cpp:121 
static int node_local_select(const std::string &path, int server_count) {
    const char *nn = std::getenv("SLURM_NNODES");
    if (!nn || !nn[0]) nn = std::getenv("SLURM_JOB_NUM_NODES");
    const char *nid = std::getenv("SLURM_NODEID");
    if (!nn || !nid || server_count <= 0) return -1;
    int nnodes = std::atoi(nn);
    int nodeid = std::atoi(nid);
    if (nnodes <= 0 || nodeid < 0 || (server_count % nnodes) != 0) return -1;
    int spn = server_count / nnodes;                 // servers per node
    if (spn <= 0) return -1;

    // ... one-time log of local_slots=[nodeid*spn, (nodeid+1)*spn) ...

    uint64_t h = fitcache_fnv1a64(path.data(), path.size());
    int slot = nodeid * spn + static_cast<int>(h % static_cast<uint64_t>(spn));

    if (slot / spn == nodeid) { g_ml_local.fetch_add(1); }   // verify locality
    else {
        g_ml_remote.fetch_add(1);
        L4C_INFO("mmap placement ANOMALY: ... slot_node=%d != requester_node=%d", ...);
    }
    return slot;
}

The locality model, line by line:

  • Under srun --ntasks-per-node=spn with block distribution, server global rank R (= SLURM_PROCID, which is also the .ports.cfg key) lives on node R / spn.
  • spn = server_count / nnodes is the servers-per-node count. The guard (server_count % nnodes) != 0 bails to -1 (→ fall through to hash) if the topology isn't a clean multiple, so we never produce a wrong slot.
  • The requester's node is SLURM_NODEID. Its local slots are the contiguous range [nodeid*spn, (nodeid+1)*spn).
  • slot = nodeid*spn + (hash(path) % spn) — hash the path to pick which of this node's servers, then offset into this node's range. So the path always lands on a server on this node, while still spreading evenly across the node's own servers.
  • The slot / spn == nodeid check is a self-audit: it recomputes the slot's node and bumps g_ml_local on success or g_ml_remote + an ANOMALY log on failure. In every reported run remote stayed 0.

This is what turns the hash baseline's "node-0 caches 18 of its 40, fallback 22" into "node-0 caches all 40, fallback 0."

4c. modulo_select() + the partitioned-access story

src/cross_job/fitcache_cross_job.cpp:82 
int modulo_select(const std::string &path, int server_count) {
    if (server_count <= 0) return -1;
    uint64_t h = fitcache_fnv1a64(path.data(), path.size());
    return static_cast<int>(h % static_cast<uint64_t>(server_count));
}

The default. server_count here spans all nodes, so the modulo scatters a path to any node — that is precisely the scatter Mechanism 2 fixes. Note this hashes over the whole cluster's slots while node_local_select hashes only within a node's slots.

Shared vs. partitioned access is not in this file — it is a property of which paths each rank opens, decided by the benchmark:

4d. Cross-epoch consistency: why the same node keeps warm-hitting

A natural worry about partitioned placement: in epoch 1 a shard is cached on node 0; in epoch 2, what stops the GPU from looking for it on node 2 and missing? The answer has two halves, and the first one usually surprises people.

A warm hit never goes to a server. In epoch 2, mmap(shard) runs fitcache_resolve_cached_path(), which computes the cached path and stats the local node's own tier directories (FitCache_NVME_PATH=/mnt/bb/$USER/... is a node-local mount) — no RPC, no routing. So "read from node 2's cache" is not a path the warm code can even take: a hit is a local file, a miss falls back to PFS. In single-job node_local mode each node is an island.

Two deterministic pieces decide where a file lives and how it is found:

  • Which node holds it — fixed at promotion time (the epoch-1 cold miss). node_local_select() routes the promotion to a server on the requester's own node via SLURM_NODEID (cross_job.cpp:121-141), so whatever node 0 reads gets copied into node 0's local tier.
  • Where on that node — the hash(path) two-level bucket (multi_source_read.cpp:302). Same path → same bucket every epoch, so the resolver always probes the right place.

The third piece is not FitCachePP's to control — whether the same node re-reads the same files. That is the application's data assignment. In the cc12m bench it is fixed by rank, computed once, then reused for every epoch (cc12m_mmap_bench.py:107,164-168):

benchmarks/dinov2/cc12m_mmap_bench.py:107 + epoch loop 
base = 0 if args.shared else rank * args.num_shards   # shard set fixed BY RANK
shard_index = [ ... ]                                 # built ONCE
for ep in range(args.epochs):                         # every epoch reuses
    for (sp, sz, members) in shard_index:             #   the SAME shard set
        ...

So rank r reads shards [r·N, (r+1)·N) in every epoch. Putting it together for two nodes:

            NODE 0  (rank 0 -> shards 0..N-1)        NODE 2  (rank 2 -> shards 2N..3N-1)
EPOCH 1     mmap shard0  -MISS->  read PFS           mmap shard2N -MISS->  read PFS
(cold)      open RPC -> node_local_select(shard0)    open RPC -> node_local_select(shard2N)
                     = a NODE-0 server -> copy to              = a NODE-2 server -> copy to
            /mnt/bb(node0)/[hash]/shard0             /mnt/bb(node2)/[hash]/shard2N

EPOCH 2     resolver stat /mnt/bb(node0)/[hash]/     resolver stat /mnt/bb(node2)/[hash]/
(warm)      -> FOUND -> HIT (local mmap, no RPC)     -> FOUND -> HIT (local mmap, no RPC)
            ^ never looks at node 2's disk           ^ never looks at node 0's disk
The one assumption that must hold. Cross-epoch reuse needs the per-node access pattern to be stable — the same node re-reads its own partition each epoch. If a pipeline reshuffled the shard-to-rank mapping every epoch, epoch-2 node 0 might want a shard that lives on node 2; node 0's resolver would stat its local disk, miss, fall back to PFS, and re-promote that shard onto node 0 — it self-heals locally, it does not reach over to node 2. You would pay a one-time cold miss per reshuffled shard. This is fine for the standard WebDataset/DDP pattern, where shards are assigned to ranks once and only the samples within a shard are shuffled, so the per-node shard set is stable. Stated as a paper assumption: warm-hit reuse across epochs assumes a per-node-stable shard partition (shard-to-rank fixed; intra-shard shuffling is fine).

5. Supporting — .meta file cache-state recovery Supporting

A .meta file is written next to each cached file so a restarted server can rebuild its cache map. It restores server-side state; the client warm-hit (Mechanism 1) is already server-map-independent, so the .meta file is not the bandwidth source.

A reader therefore sees either the old .meta file or the new one, never a torn one. The per-pid temp suffix avoids collisions between concurrent server processes on the same node. 5d. The persist_meta_enabled() gate

.meta file write + restore is decoupled from the heavyweight cross-job machinery, at cross_job.cpp:171:

src/cross_job/fitcache_cross_job.cpp:171 
bool persist_meta_enabled() {
    static int cached = -1;
    if (cached < 0) {
        const char *v = std::getenv("FitCache_PERSIST_META");
        int explicit_on = (v && std::strcmp(v, "1") == 0) ? 1 : 0;
        cached = (explicit_on || cross_job_enabled()) ? 1 : 0;   // auto-on under cross-job
    }
    return cached != 0;
}

Why this exists: the original gate ran the full cross-job stack (registry init + heartbeat + sibling-refresh threads) for any test that merely wanted .meta file persistence, and those background threads skewed Horovod ranks at n=32768/1N. FitCache_PERSIST_META=1 turns on just the .meta file write + restore — no registry, no peer-lookup, no extra threads — so a single-job run can get cache durability across restart without the latency tax. It is auto-on under cross-job (which needs the .meta files for peer discovery anyway).
