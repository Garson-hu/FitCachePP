## Headline result: **45% cold-epoch reduction, 14% per-job wall reduction**

| Metric | Single-job baseline | Two-job concurrent | Δ |
|---|---:|---:|---:|
| Cold epoch | 362 s | ~199 s | **−45%** |
| Per-job wall | 19m00s | 16m19s | **−14%** |
| Aggregate I/O work (2 jobs sequentially vs concurrent) | 38m00s | 16m19s | **−57%** |

Both jobs' cold epoch dropped from 362s to ~199s — almost exactly half.
Mechanism: HRW deterministically picks the same server for any given
path across both jobs (same dataset, same global live set, identical
node_uuid + rank tuples). Whichever job opens a file first incurs the
PFS read; the other job hits the warmed cache. Aggregate cold work is
roughly halved, which is what the cold-epoch wall reflects.

## Cross-job indicators

`peer_lookup` queries received: **0** across all 8 servers.
`Open RPC redirect` issued: **0**.

This is **expected** for a stable live set. HRW assignment is
deterministic across jobs, so each path always lands on the same
server, and that server has the file cached after the first read from
either job. No need for the peer-lookup fanout / redirect path; the
HRW + cluster-registry coordination is sufficient by itself.

The peer-lookup / redirect path only fires under **server-set churn**
(e.g., a server joins after the cache was warmed and HRW for some paths
now picks the new server). The localhost smoke harness in
`scripts/run_two_server_smoke.sh` artificially induces churn by
starting S2 only after S1 has cached files; that's where the redirect
path was end-to-end tested.

`sidecar_writes` log lines: 0 visible at FitCache_LOG_LEVEL=500 (NOTICE
priority filters out the INFO-level "wrote sidecar" line). Sidecars
should still be on disk — verifiable by `find /mnt/local/.../*.meta`
on c70/c71 while the next experiment is queued; not done here because
ssh to compute nodes is denied after the job exits.

## Caveats / interpretation

1. Both nodes (c70, c71) report the same `/etc/machine-id`
   (`72f968c7f1034e719b00dea1e1471049`) — typical for cloned cluster
   images. With identical (node_uuid, rank) tuples across nodes, HRW
   scores tie and `hrw_select`'s strict `>` tie-break sends paths to
   whichever entry was added to `g_endpoints` first. In practice this
   means Job A's clients and Job B's clients route to the SAME node
   (likely c70, registered first per the heartbeat ordering). c71's
   servers do little work in this configuration.

   That doesn't change the cross-job-sharing-reduces-aggregate-IO
   result — the headline is real — but it means the routing isn't
   load-balanced across nodes the way HRW intends. Fix would be to
   inject something node-specific into the HRW input besides
   `node_uuid` (e.g., the registered Mercury addr's IP, or the
   hostname, or just have the cluster admin set distinct
   `/etc/machine-id`).

2. Per-job wall-clock improvement (14%) is smaller than aggregate
   improvement (57%) because each job still has to walk through its
   own full epoch of training; only the I/O-bound parts benefit. This
   matches the IPDPS paper's scaling analysis: cache helps when I/O
   is the bottleneck.

3. With 8 servers consolidated onto one node (because of the
   node_uuid issue above) and one client GPU per node, the per-server
   bandwidth could be a contention point. Hasn't been measured here.
