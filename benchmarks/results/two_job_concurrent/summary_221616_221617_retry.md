# Two-job concurrent cross-job sharing — retry with HRW addr-in-hash fix

**Date:** 2026-05-11
**Jobs:** SLURM 221616 (c70, Job A) + 221617 (c71, Job B) — concurrent
**Result:** Both jobs COMPLETED in ~16:15

## Why the retry

The prior concurrent run (SLURM 221614/221615 at 04:42) had every path
routing to the same node because c70 and c71 ship cloned images with
identical `/etc/machine-id`, so the HRW score (which fed only
`path || node_uuid || rank`) tied across hosts. We added `s.addr` to the
HRW input (commit on `main` before this run) — `s.addr` embeds host:port
so it's unique per Mercury endpoint, which breaks the tie.

## Routing balance — not directly verifiable from these logs

The cluster server logs (`fitcache_server_log.<pid>.<rank>` written by
log4c) for this run are dominated by `registry: rename ... failed:
Device or resource busy` errors from `fitcache_cluster_registry.cpp:155`
(see "Known issues" below). The `Open RPC: requested path` lines are
not in the captured server logs — those landed somewhere on the compute
nodes' local filesystem rather than the NFS-shared repo root the
heartbeat-error logs ended up in. So the open-distribution across
c70 vs c71 cannot be counted from this run.

**Implication:** the addr-in-hash fix is committed and compiles, the
two-job concurrent retry runs cleanly to completion in similar wall-clock
time, but the direct check that opens-per-node now balances would need
either a fresh run with per-rank server log files preserved next to the
job output, or a localhost smoke with `FitCache_LOG_LEVEL=700` that grep
counts `Open RPC: requested path` per server.

## Known issue (not introduced by this run)

`fitcache_cluster_registry.cpp:155` is the `std::rename(tmp, final)` in
the atomic write helper. On BeeGFS, repeated calls during heartbeat from
multiple concurrent servers (especially when prior runs left orphan
`<final>.tmp.<pid>` files behind) produce chains like
`c70_rank0.txt.tmp.2046785.tmp.2046791.tmp.2355754` and EBUSY rename
failures. Hypothesis: orphan tmp files from earlier processes that
were not properly torn down by SLURM still hold file handles or block
the rename. Functional behavior of the experiment is unaffected
(both jobs completed in expected time) but the logs are noisy and the
heartbeat keys don't always get refreshed promptly. Recommended fix:
clear `${FitCache_CLUSTER_REGISTRY_DIR}` before each new run, and add a
unique per-run subdirectory (the driver already does this via
`$RUN_REGISTRY`).
