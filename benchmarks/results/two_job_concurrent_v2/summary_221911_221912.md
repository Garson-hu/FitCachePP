### Aggregate across both jobs

- opens_total: **93,212**
- local_hit: **82,248 (88.2%)** — the dominant sharing pathway. With both jobs registered against the same shared cluster registry, HRW deterministically sends the same path to the same physical server across jobs. Whichever job warms a file first, the other job's open becomes a local hit on that same server. Cross-job sharing is collapsed into the local-hit counter for ~88% of opens.
- redirect_to_peer: **1,042 (1.1%)** — peer-redirect fallback path. Fires when a server's path_cache_map hasn't yet observed a file that a sibling on a different node already cached (the sibling-cache-refresh thread merges sidecars on a 10s cadence; redirect handles the gap).
- peer_lookup has_yes: **3,802** — peer responses confirming "i have this file". The total peer-lookup-handled across both jobs is 75,361; **5% of peer lookups land a positive answer**, meaning peer-cache sharing is materially active even after most reads are local-hits.
- pfs_fallback: **9,922 (10.6%)** — direct PFS reads. Tightly bounded: flat at this total from +10 min through end-of-run. The cold-load phase ended cleanly and **no additional PFS reads accrued after the first epoch**.

## Defended claim (and one we are NOT claiming)

**Defended:** *two concurrent jobs against the same dataset, registered against a shared cluster registry, share a single warmed cache and stop generating new PFS reads after the cold-load phase.* Aggregate PFS bytes read is bounded rather than growing with elapsed time.

**Not defended by this run:** *cross-job sharing speeds up individual jobs.* At n_train=8192 on a single RTX 4060 Ti, CosmoFlow is GPU-bound and there is no headroom for I/O to move per-epoch wall-clock. To support a per-job speedup claim we would need a workload regime where I/O is the bottleneck (larger dataset, faster GPU, or a workload like Megatron-LM where token throughput is more bandwidth-bound).
