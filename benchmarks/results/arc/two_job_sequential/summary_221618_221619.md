**Date:** 2026-05-11
**Jobs:** SLURM 221618 (Job A, c66, FINISHED) + 221619 (Job B, c66, depends-on A)
**Result:** Designed to defend the sidecar-rebuild-survives-job-boundary
claim. **The experiment did not exercise FitCache at all** — see below.

The mechanism under test was: Job A populates the local NVMe cache and
writes sidecars; Job A exits and SLURM frees the node; Job B starts on
the same node, scans the sidecars at startup
(`fitcache_data_mover_restore_from_sidecars`), rebuilds

(~199s).

What we observed: Job B's epoch-0 is 200s — essentially identical to Job
A's epoch-0. **No warm-start speedup.**

## Root cause — FitCache was not engaged

Direct evidence the FitCache server pathway was dormant for both jobs:

- On c66, after Job A finished:
  ```
  $ find /mnt/local/ghu4/fitcachepp_dram_seq_*  -type f       → 0 files
  $ find /mnt/local/ghu4/fitcachepp_nvme_seq_*  -type f       → 0 files
  $ find /mnt/local/ghu4/fitcachepp_*_seq_* -name '*.meta'    → 0 sidecars
  ```
  Job A's data mover never copied a single file into either tier dir,
  and never wrote a single sidecar. So there was nothing for Job B to
  restore.

- In the server log4c output for Job B's currently-running fitcache_server
  processes (PIDs 2187826, 2187828, 2187830, 2187832 on c66, log files at
  `/home/ghu4/hvac/FitCachePP/fitcache_server_log.<pid>.0`):
  ```
  Open RPC: requested path     → 0 occurrences
  Data mover: Moving file       → 0 occurrences
  Data mover: Copied            → 0 occurrences
  ```
  The server is up, registered, and heartbeating. It's just never
  receiving any client opens.

Same pattern holds for **every** cluster experiment in the session: the
log4c files for PIDs 2034936/2034938 (the original concurrent jobs
221614/221615 advertised as defending cold-epoch -45%), 2355754 et al.
(the concurrent retry), and 2187826 et al. (current sequential Job B)
all show zero Open RPC counts. **No cluster experiment in this session
has exercised the FitCache open path.**

## Where the disconnect is — most likely cause

The script exports `FitCache_DATA_DIR` to
`/mnt/beegfs/ghu4/hvac/cosmoUniverse_2019_05_4parE_tf_v2_mini/train_61440/train/`
but the training-script config (`configs/cosmo.yaml`, loaded by
`train.py`) reads:
```
data:
  data_dir: /mnt/beegfs/ghu4/hvac/cosmoUniverse_2019_05_4parE_tf_v2_mini/train_1024
```

`train_1024` is NOT under `train_61440/train/`. If the FitCache client
(`libfitcache_client.so`) only intercepts opens whose path is under
`FitCache_DATA_DIR`, every read passes through to BeeGFS directly,
bypassing the FitCache server entirely. That matches every symptom:
- ports.cfg files written (servers started)
- heartbeat in the registry
- BUT zero opens, zero copies, zero sidecars

To verify: check the path-filter logic in `fitcache_client.cpp` / the
LD_PRELOAD shim, and either point `FitCache_DATA_DIR` at the path
`train.py` actually reads (`train_1024`), OR change the path filter to
match the longer prefix.

## What the consistent 200s/188s pattern means

If FitCache isn't engaged, the 200s cold-epoch / 188s warm-epoch pattern
across all cluster runs is just standard CosmoFlow GPU-warmup +
TensorFlow autotuner stabilization + BeeGFS metadata being kernel-page-
cached after the first read. None of it is FitCache-attributable.

The "cold epoch -45% (362→199)" finding from the prior session was
likely an artifact of the first run hitting a cold BeeGFS metadata cache
on c66 and subsequent runs benefiting from kernel page cache warmth, not
FitCache cross-job sharing.
