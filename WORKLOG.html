2026-05-19 — TPDS contribution pivot: mmap interceptor + sidecar warm-restart land as the two new mechanisms; cross-job becomes future work

After the cross-job campaign concluded with weak wall-time savings + recurring DataLossError flakiness (see 2026-05-17 / 2026-05-18 entries below), the TPDS contribution shape was revised. Two new mechanisms now anchor the paper, with cross-job sharing demoted to secondary / future work:

  1. Primary new contribution — mmap interceptor + LLM workload generalization. The IPDPS-paper FitCache intercepted only {open, read, pread, close}; page-fault reads from mmap-based loaders (numpy.memmap, Megatron IndexedDataset, DINOv2 ImageNet tarballs) silently bypassed the cache. The src/client/wrappers.c::mmap intercept allocates an anonymous region and eager-populates it via ms_read at mmap() time. Validation: bit-identical Megatron lm_loss=6.1157 between FitCachePP and Pure_CF; 11.5× cold-state throughput (894 MB/s vs 78 MB/s) on a 10 GB synthetic Megatron IndexedDataset; 1.93× amortized over 20 K iterations × batch 16 × seq 1024.
  2. Second technical contribution — persistent sidecar metadata + warm-restart recovery. Each cached file gets a .meta sidecar (magic + version + original_path + original_size + cached_at_unix + access_count) written atomically alongside the data file. On server startup, restore_from_sidecars() scans the tier directories and rebuilds path_cache_map so the next training process hits the cache without refetching from PFS. Validation run (2026-05-19): Phase 1 cold (empty cache) epoch wall 340 s → kill server → Phase 3 warm-after-restart (scanned 33,789 sidecars) epoch wall 260 s (= warm-baseline 285 s within noise, 80 s faster than cold-from-empty). Mechanism rebuilt path_cache_map with 33,789 entries on every one of the 4 server ranks.
  3. Future / secondary — cross-job sharing. Mechanism is functional and validated end-to-end (peer_lookup, redirect_to_peer, has_yes counters work as designed). Wall-time benefit is structurally bounded (I/O fraction of cold epoch + consumer local-cache absorption). Concurrent mode has a recurring DataLossError: inflate() failed that is un-root-caused. Kept in the paper as secondary prototype evidence / future work.

Engineering change that enabled the sidecar validation: decoupled sidecar write + restore from FitCache_CROSS_JOB. The original gate ran the cross-job machinery (registry init + sibling-refresh threads) for any test that wanted sidecar persistence; those threads skewed Horovod ranks 2 + 7 at n=32768/1N. New flag FitCache_PERSIST_META=1 (auto-on under cross-job; opt-in otherwise) gates just the sidecar write + restore. Code: bool persist_meta_enabled() in src/cross_job/fitcache_cross_job.{h,cpp}; gate replaced at src/server/fitcache_data_mover.cpp:512 and src/server/fitcache_server.cpp:179. 16/16 cross-job smoke tests pass.

Operational note: the Frontier queue parked the original sidecar validation 19 hours behind other jobs for a ~13-minute experiment. Rule encoded: under QOS=debug, cancel + resubmit whenever a pending job's start time is many hours away while its time limit is short.

  • LLM dataloader benchmark (10 GB synthetic Megatron IndexedDataset): FitCachePP cold 894 MB/s vs Pure_CF cold 78 MB/s = 11.5× cold-state speedup; amortized over 20 K iters 1.93× (855 vs 443 MB/s). Built generate_synth_corpus.py + llm_dataloader_bench.py.

One clean data point stands (consumer cold 338 s vs single-job 352 s, −14 s). Concurrent-mode DataLossError is a real defect, un-root-caused.

2026-05-17 — 4-servers-per-node fix unblocks n=32768; cross-job speedup scales 9× at larger dataset; multi-node weak-scaling clean; Megatron + DINOv2 re-verified

  • 4-servers-per-node fix landed and unblocks n=32768. A single server progress thread serialised RPC handlers on slow Lustre open() under MDS contention. Bumping SERVERS_PER_NODE=4 distributes the hashring across four progress threads. n=32768 single-job then completed: cold 366 s, warm 285 s, wall 708 s, 65,764 opens, no stall.

Real DAX-mode PMem hardware evaluation on c35. Two sustained-read micro-benchmarks: warm-vs-cold 0.13× (local /tmp source) and 0.21× (BeeGFS source). The cache-hit path pays ~250 ms per-open RPC overhead; PMem vs NVMe doesn't matter at this granularity. Tier placement on real PMem works end-to-end. CosmoFlow follow-up infeasible: c35 has DAX PMem but no GPU; GPU nodes have no DAX PMem.

Workload-generalization (Megatron-LM + DINOv2) — architectural limit. Both use mmap-based zero-copy reads; the LD_PRELOAD client intercepts open/read/pread but not mmap, so page-fault reads bypass FitCachePP. Three options for the paper: drop these workloads, add an mmap interceptor, or reframe the contract as syscall-based-I/O only. (The mmap interceptor was later chosen — see 2026-05-19.)

2026-05-11 (latest) — Post-engineering hardening pass: HRW addr-in-hash, cross-job telemetry, PMem tier

Picked up after a two-job concurrent run surfaced a routing collapse: identical /etc/machine-id across hosts made node_uuid identical, so the HRW score tied across hosts and all paths landed on whichever host registered first. Five changes landed:

  • HRW addr-in-hash fix. Appended s.addr (the Mercury endpoint string, unique per endpoint) to the HRW input. Breaks the tie; preserves behaviour for clusters with distinct machine-ids.
  • Cross-job telemetry counters. Eight atomic counters for open + peer-lookup events; periodic info line emitted from the heartbeat thread when FitCache_CROSS_JOB=1, gated so single-job runs stay silent.
  • Bit-equivalence smoke. Same 8-file workload with FitCache_CROSS_JOB=0 and =1; per-file sha256 of cached payloads matches across passes and against source. PASS.
  • Opt-in PMem tier. Added CACHE_TIER_PMEM=4; placement priority DRAM → PMem → NVMe; restore-sidecars scans the PMem dir; eviction reaper handles the third tier. Dormant when env vars unset.
  • Three-tier pilot scripts. Local smoke verified 4/4/4 placement split across DRAM/PMem/NVMe and full restoration of all 12 files from sidecars per-tier across server restart. Cluster pilot deferred (no node with both GPU and DAX PMem).

MAJOR FINDING: every cluster CosmoFlow run in this session executed with zero FitCache Open RPCs. Likely root cause: FitCache_DATA_DIR points at train_61440/train/ but train.py reads train_1024 per configs/cosmo.yaml, and the LD_PRELOAD path filter doesn't match — all reads pass through to BeeGFS direct. Implication: the prior "cold epoch −45%" / "per-job wall −14%" / "aggregate −57%" numbers should NOT be quoted until the path-filter mismatch is fixed and reruns verify the pathway is engaged. What is still defended: bit-equivalence smoke, three-tier local smoke, unit smoke suite, and the HRW addr-in-hash fix.

2026-05-11 (later) — End-to-end cross-job sharing proven on Mercury; cluster experiments started

Multi-server localhost smoke harness — the first real Mercury test of the cross-job redirect path. Surfaced and fixed three bugs:

  1. Silent hang on lookup_addr=NULL. Three RPC functions returned without firing the per-file sync context when lookup returned NULL, blocking the caller forever. Now all three signal -1 so the wait unblocks.
  2. std::string global state silently zeroed mid-process. Registry globals had their heap-backed c_str() become "" between write and first read. Workaround: fixed-size char[1024] buffers with thin getters, never reallocated after init.
  3. ms_read missing peer-slot override. Reads on a redirected fd went back to the HRW-chosen server. Fixed: ms_read now consults the peer-slot override before HRW selection.

Smoke harness result: 5 peer_lookup hits, 5 server-side redirects, 5 client-side redirects handled, all 8 files read end-to-end. Cross-job sharing proven on real Mercury for the first time.

First cluster experiment: single-job baseline on c66, epochs 362 / 189 / 188 / 188 / 186 s, cold/warm speedup 1.93×; peer_lookup and sidecar counters correctly zero in single-job mode.

2026-05-11 — Cross-job extension engineering work complete (four mechanisms)

Four commits land the open-time peer-fanout path, persistent sidecar metadata, refcount-respecting eviction, and the subscriber-lease machinery (~1,500 LOC, within the ~1,600 LOC budget).

  • Open-time peer-lookup fanout. Server-side async state machine: on path_cache_map miss with cross-job on, fan out fitcache_peer_lookup_rpc to every live peer; first has=1 wins, open returns FITCACHE_OPEN_REDIRECT plus the peer's Mercury addr. Client registers the peer addr as a routing slot and re-issues the open.
  • Persistent sidecar metadata. New module: atomic write (tmp+fsync+rename), magic+version-validated read, flock-serialised refcount RMW, directory scan that quarantines corrupt sidecars to .broken. Server startup scans DRAM + NVMe paths and rebuilds path_cache_map + used-bytes counters.
  • Refcount-respecting eviction + background reaper. Picks lowest-access_count among refcount=0 sidecars; refcount>0 files protected. Reaper thread runs every FitCache_REAPER_SEC (default 30 s) until used bytes drop below the low watermark.
  • Subscriber-lease management. Subscribe/release compute a lightweight dataset_id and insert/remove a subscriber record with a renewing lease. Collapsed the spec's RPCs into direct PFS-backed registry writes since the registry is already PFS-backed.

Smoke test: 8/8 pass (FNV vectors, HRW balance + churn vs modulo, dataset_id, registry roundtrip, client-side routing, sidecar write/read/refcount/scan/quarantine, eviction victim selection, subscriber-lease roundtrip).

Backward compatibility: every new path gated by cross_job_enabled(); FitCache_CROSS_JOB=0 keeps single-job builds bit-identical to IPDPS at runtime.
