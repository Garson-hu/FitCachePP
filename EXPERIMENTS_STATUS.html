Contribution 1 — Transparent mmap Cache Path DONE

An LD_PRELOAD client transparently redirects mmap to a node-local cached copy on a warm hit (fitcache_resolve_cached_path(): client-side, deterministic hash-bin, size-match completeness gate, no RPC), and falls back to native PFS mmap on a cold miss while promoting the file for next time. The cache is tier-general — the data mover places a promoted file DRAM (tmpfs) first, then PMem, then NVMe, by capacity, and the resolver probes the tiers in that order and maps whichever holds the file. On Frontier the warm tier was the per-node NVMe burst buffer (/mnt/bb). What matters is the per-node working set: these sweeps keep it > the 512 GiB node RAM on purpose by replicating it on every node (Megatron all 40 shards = 640 GiB/node; GNN whole feature files ~902 GB/node; DINOv2 full-corpus shared, 541 GB/node), so aggregate DRAM across nodes does not shrink it and per-node tmpfs cannot hold it (PMem unset). A partitioned pattern (DINOv2 disjoint = the Access-Aware placement) is the exception — ~34 GB/node at 16 nodes fits tmpfs — but then the Native_mmap_PFS baseline page-caches it too and the sustained gap washes out, so NVMe is the right tier for the sustained claim. Two views are reported for every result: warm-hit-only (mechanism) and amortized including pre-stage cost. Every cell passes a hard FitCachePP-vs-Native checksum-equality gate plus a decode gate where applicable.

Contribution 2 — Access-Aware mmap Cache Placement DONE

A warm-hit needs the cached file on the requester's own node. Default hash placement scatters a node's mmap set across the cluster. Access-aware placement (FITCACHE_MMAP_PLACEMENT=node_local branch in select_server_for_path(), src/cross_job/fitcache_cross_job.cpp; default hash unchanged) routes promotion to node-local servers. Two access patterns are covered: shared (all nodes read the same set, each replicates locally) and partitioned (nodes read disjoint sets, each caches only its own).

Headline. The mmap path provides the steady-state access speedup; access-aware placement ensures the data is actually node-local. Placement eliminates hash scatter (per-node fallback 0, remote 0) while avoiding unnecessary replication for partitioned access: partitioned DINOv2 N=2 gives full local mmap hits at duplicate factor 1.0× (global unique 996 = node0 [0,497] + node1 [498,995]), versus shared mode's 2.0×. Shared local replication is a deliberate tradeoff; partitioned avoids full replication. Placement only; the sidecar and organic-promote path are unchanged. Supporting Mechanism — Sidecar-Based Cache-State Recovery Supporting

A .meta sidecar is written per cached file by the data mover on organic promotion. After a FitCachePP metadata-service restart, restore_from_sidecars rebuilds the server-side cache-state map so original PFS paths warm-hit local NVMe again. This restores reusable cache state and reduces cold metadata recovery; it is not the source of the warm-hit bandwidth and does not improve every epoch. The client warm-hit resolver is server-map-independent. Harness: scripts/frontier/frontier_sidecar_recovery.sh. Result base: benchmarks/results/frontier/sidecar_recovery/.

Superseded / Do Not Cite Superseded

  • Eager-populate mmap (server + Mercury anon-mmap) path — replaced by the warm-hit direct local-tier redesign. It added a PFS→server→client hop and could not beat Native_mmap_PFS in any single-pass regime.
  • 1 TB sharded Megatron sweep (16 GiB shards) — INVALID. Hit the ~2 GiB read-truncation bug; FitCachePP read only ~1/8 of each shard and zero-filled the tail. The "order-of-magnitude speedup" was an artifact. Fixed (server short-read loop + ≤1 GiB chunked populate) and superseded by the warm-hit sweep above.
  • 10 GB single-file Megatron compare — same truncation bug; demoted.
  • 950-shard / 95.4% DINOv2 single-node run — superseded by the 100%-corpus (996/996) sweep.
  • 32-shard / partial-coverage DINOv2 passes — retained only as a coverage table; the full-corpus result is the reported one.
  • 216 MB synthetic DINOv2 I/O run — compatibility-only; never a valid performance result.
