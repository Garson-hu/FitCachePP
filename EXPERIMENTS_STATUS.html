Contribution 1 — Transparent mmap Cache Path DONE

An LD_PRELOAD client transparently redirects mmap to a local-NVMe cached copy on a warm hit (fitcache_resolve_cached_path(): client-side, deterministic hash-bin, size-match completeness gate, no RPC), and falls back to native PFS mmap on a cold miss while promoting the file for next time. Two views are reported for every result: warm-hit-only (mechanism) and amortized including pre-stage cost. Every cell passes a hard FitCachePP-vs-Native checksum-equality gate plus a decode gate where applicable.

Mechanism / honesty. Magnitude is bounded by the PFS access pattern. Random small reads on Lustre (GNN ~3–4 MB/s per faulted page) are where local-NVMe direct mmap wins biggest (18–33×); dense-sequential reads (Megatron, DINOv2) win modestly (~1.3–1.6×) because Frontier Lustre sequential bandwidth is already high. The full-corpus DINOv2 run uses a working set > node RAM, ruling out a page-cache artifact. Claims are scoped to mmap-backed data loading, not end-to-end model training. Result base: benchmarks/results/frontier/{megatron,gnn,dinov2}_warmhit_sweep/.

Contribution 2 — Access-Aware mmap Cache Placement DONE

A warm-hit needs the cached file on the requester's own node. Default hash placement scatters a node's mmap set across the cluster. Access-aware placement (FITCACHE_MMAP_PLACEMENT=node_local branch in select_server_for_path(), src/cross_job/fitcache_cross_job.cpp; default hash unchanged) routes promotion to node-local servers. Two access patterns are covered: shared (all nodes read the same set, each replicates locally) and partitioned (nodes read disjoint sets, each caches only its own).

Headline. The mmap path provides the steady-state access speedup; access-aware placement ensures the data is actually node-local. Placement eliminates hash scatter (per-node fallback 0, remote 0) while avoiding unnecessary replication for partitioned access: partitioned DINOv2 N=2 gives full local mmap hits at duplicate factor 1.0× (global unique 996 = node0 [0,497] + node1 [498,995]), versus shared mode's 2.0×. Shared local replication is a deliberate tradeoff; partitioned avoids full replication. Placement only; the sidecar and organic-promote path are unchanged. Result base: benchmarks/results/frontier/sidecar_recovery/*_{nodelocal,partitioned}/.

Supporting Mechanism — Sidecar-Based Cache-State Recovery Supporting

A .meta sidecar is written per cached file by the data mover on organic promotion. After a FitCachePP metadata-service restart, restore_from_sidecars rebuilds the server-side cache-state map so original PFS paths warm-hit local NVMe again. This restores reusable cache state and reduces cold metadata recovery; it is not the source of the warm-hit bandwidth and does not improve every epoch. The client warm-hit resolver is server-map-independent. Harness: scripts/frontier/frontier_sidecar_recovery.sh. Result base: benchmarks/results/frontier/sidecar_recovery/.

Superseded / Do Not Cite Superseded

  • Eager-populate mmap (server + Mercury anon-mmap) path — replaced by the warm-hit direct-NVMe redesign. It added a PFS→server→client hop and could not beat Native_mmap_PFS in any single-pass regime.
  • 1 TB sharded Megatron sweep (16 GiB shards) — INVALID. Hit the ~2 GiB read-truncation bug; FitCachePP read only ~1/8 of each shard and zero-filled the tail. The "order-of-magnitude speedup" was an artifact. Fixed (server short-read loop + ≤1 GiB chunked populate) and superseded by the warm-hit sweep above.
  • 10 GB single-file Megatron compare — same truncation bug; demoted.
  • 950-shard / 95.4% DINOv2 single-node run — superseded by the 100%-corpus (996/996) sweep.
  • 32-shard / partial-coverage DINOv2 passes — retained only as a coverage table; the full-corpus result is the reported one.
  • 216 MB synthetic DINOv2 I/O run — compatibility-only; never a valid performance result.
